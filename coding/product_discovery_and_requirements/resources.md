# Resources

**Status:** Second draft

Stage-specific material — worked examples, web references, agent rule sets, and books — lives in the **Further material** section at the end of each stage document. This file holds only what is cross-cutting: where to start, which technique fits which uncertainty, and how to judge whether a method is worth adopting.

## Reading order

If new to the whole lifecycle, read in this order (each title is discussed in its stage document's Further material):

1. *Continuous Discovery Habits* — Teresa Torres ([product discovery](./product_discovery.md))
2. *User Story Mapping* — Jeff Patton ([use cases and story mapping](./use_cases_and_story_mapping.md))
3. *Writing Effective Use Cases* — Alistair Cockburn ([use cases and story mapping](./use_cases_and_story_mapping.md))
4. *Software Requirements*, 3rd ed. — Karl Wiegers, Joy Beatty ([requirements engineering](./requirements_engineering.md))
5. *Testing Business Ideas* — David J. Bland, Alexander Osterwalder ([product discovery](./product_discovery.md))
6. *Learning Domain-Driven Design* — Vlad Khononov ([domain discovery](./domain_discovery.md))

## Practical technique index

| If the uncertainty is about…                 | Start with…                                            |
| -------------------------------------------- | ------------------------------------------------------ |
| Whether a problem is valuable                | Interviews, observation, JTBD, current-journey mapping |
| Which opportunity to pursue                  | Opportunity Solution Tree, outcome mapping             |
| Whether a proposed solution will work        | Assumption mapping and targeted experiments            |
| End-to-end product scope                     | User story mapping                                     |
| Complex actor interactions                   | Use cases and scenario walkthroughs                    |
| Tacit business behavior                      | EventStorming, Domain Storytelling, example mapping    |
| Conflicting terminology or ownership         | Glossary, capability map, context map                  |
| Architectural risk from non-functional needs | Quality-attribute scenarios and utility tree           |
| Contractual or regulated completeness        | Requirements engineering and traceability              |
| Which lifecycle a specific topic needs       | [Lifecycle tailoring](./lifecycle_tailoring.md)        |
| What to commit to next, and in what order    | [Product definition](./product_definition.md)          |
| Whether a shipped release created value      | [Validation and feedback](./validation_and_feedback.md) |

## Evaluation rule

Adopt a method when it reduces an important uncertainty or improves a consequential decision. Do not adopt it solely because its artifact looks complete. Scale ceremony with risk, irreversibility, regulation, coordination cost, and product lifetime.
