## 1. Goal

Build a skillset/workflow that implements the **discovery–definition–requirements loop** from the [overview](../overview.md) as agent skills, extending the two existing vision-stage skills:

- [`brainstorm-vision`](../../../skills-plugins/brainstorm-vision/SKILL.md) — divergent vision brainstorm → `*-foundation-vision.md` (the slow-changing anchor)
- [`create-vision-companion`](../../../skills-plugins/create-vision-companion/SKILL.md) — frozen vision → derived companion bundle (`*-vision-ai-spec/`: actors, glossary, invariants, capability map, UC/vision indexes)

Today the lifecycle's top box is covered; the fast loop underneath is not. The skillset adds the loop stages — **product discovery**, **product definition**, **requirements engineering** — plus the **lifecycle tailoring** entry step and the **validation** re-entry, wired together by the companion bundle's stable ID scheme.

### Design principles

1. **Two skill modes, chosen per stage.** *Interview skills* (the `brainstorm-vision` / `grill-me` pattern) where the human supplies knowledge the agent cannot have — evidence, priorities, business judgment. *AFK derive skills* (the `create-vision-companion` pattern: orchestrator + builder/critic sub-agents, `decisions.md`, human reviews at the end) where the work is restructuring already-captured content. Discovery and definition are interview-heavy; specification and index maintenance are derive-heavy.
2. **The companion bundle stays derived-only.** Loop artifacts are *not* derivable from the frozen vision (they add evidence and commitments), so they live in a separate **loop workspace**, citing companion IDs. The `*-vision-ai-spec/` bundle is never extended with loop content.
3. **One traceability spine, extended.** The companion's IDs (`S#`, `V#`, `UC#`, `BV#`, `INV#`, `CAP#`) are the anchor. The loop adds its own ID families (below) and every loop artifact cites upward: opportunity → outcome/vision, solution → opportunity, assumption → solution (or opportunity only when solution-independent), experiment → assumption + applicable solution, capability-in-scope → opportunity + evidence, requirement → capability/UC.
4. **Reuse existing skills as loop steps.** `prototype` (discovery's "test cheaply"), `domain-modeling` (domain discovery), `grill-with-docs` (requirements validation), `qa` / `triage` (validation intake). The new skills orchestrate around them, not replace them. Skills that belong to later phases (design, implementation planning) are *not* part of this skillset — see §7.
5. **Ceremony is tailored, not fixed.** The tailoring step decides which loop skills a topic actually runs; skills must degrade gracefully to a low-ceremony solo-developer setting ([minimum useful discovery package](../overview.md#minimum-useful-discovery-package)).
6. **The method docs in the parent folder are the skills' source material — all of them.** Each skill *must* consume its stage doc(s): templates become the skill's output shapes, completion checks become its finalize gates, failure modes become its guardrails. §2.1 maps every method document in the parent folder to its consuming skill so nothing is orphaned. (Mechanism — distill into skill sub-files at authoring time with a source pointer, vs. read the docs live at runtime — is an open question, §8.)
7. **No artifact may share a name with a method doc.** The method docs in the parent folder describe *how to do the work*; the artifacts (product repo, `docs/product/<topic>/`) record *the work done for one product*. Identical filenames invite confusion, so artifact names must differ from every method-doc name. The one existing collision — the companion bundle's `glossary.md` vs. the method [glossary.md](../glossary.md) — is resolved by renaming the artifact to `domain-glossary.md` (part of the `create-vision-companion` adjustments, §5.2).

Domain-discovery artifacts (glossary, rules, context boundaries) are deliberately **not** duplicated here: the companion's `domain-glossary.md` (renamed from `glossary.md`, §5.2) + the repo's `CONTEXT.md`/ADRs (via `domain-modeling`) remain canonical, and loop skills consult/extend those.

**`SOL#` representation decision.** Solution directions get their own `solutions.md`, not a section of `opportunities.md`. Rationale: (a) the opportunity map must stay solution-neutral — folding solutions into it would undermine that guardrail; (b) the workspace's existing pattern is one artifact per ID family, and `SOL#` follows it; (c) the `create-vision-companion` ledger already anticipates the file by name — its §3.4 excludes `solutions.md` from bundle derivation. The `SOL#` model enforces ≥3 materially different directions (incl. process/policy/manual-service/no-build) or an explicit `DEC#`, the `OPP → SOL → ASM → EXP` trace layer, and retention of rejected/parked directions with reasons — linter-visible, never silently deleted.

The `SOL#` model above is enforced mechanically by the deterministic workspace linter — §2.2, checks LNT-01 (ID format/uniqueness), LNT-03 (citation integrity), and LNT-07 (the full `OPP → SOL → ASM → EXP` chain including the ≥3-directions-or-`DEC#` rule).

**Strategy representation decision.** The vision's thin ordered-outcomes strategy section (the *Strategy (ordered outcomes)* template section of [product_vision.md](../product_vision.md)) gets **no new ID family**: strategy entries are an ordered field set — *outcome — target segment — why this order* — living in the foundation vision one-pager (elicited or stubbed by `brainstorm-vision`) and derived and indexed under the existing `vision-index.md`, each entry citing the vision IDs (`V#`/`S#`) it orders. Rationale: (a) the strategy's content *is* its ordering, and reordering it is a routine discovery pivot (§4.2) — a durable per-entry ID family would turn routine reordering into spine churn and invite the deliberately thin section to grow into a fourth artifact; (b) `brainstorm-vision` writes only `S/V/UC/BV` and cites, never writes, loop IDs — a new vision-side family would reopen its spine-preservation contract, LNT-01's family list, LNT-02's reservations, and the companion's Phase 0 inventory for a list that is expected to change often; (c) the derived-only companion already owns the index mechanism, and the downstream strategy checks (§5.4, §5.5) are judgment gates reading the *current* order plus the cited vision IDs, not durable citations to individual strategy entries. Consequences: LNT-02's reserved-family list is **unchanged** — no new family exists to sync; the companion reserves the strategy *field set* in its vision-index schema rather than an ID family; an index that omits a present strategy section fails the bundle-completeness check (LNT-04); a stubbed section carries the canonical `OPEN:` marker (LNT-05). No new LNT check is needed.

### 2.2 Deterministic workspace linter

A **script, not an LLM skill** — working name `lint-workspace`; implementation language is an authoring decision — vendored with the skillset. It parses the companion bundle (`*-vision-ai-spec/`) and the loop workspace and reports pass/fail per check, naming the offending file and ID. It is the shared implementation of the companion's Phase 9 mechanical gates and of every loop skill's deterministic finalize checks.

**Deterministic vs. judgment.** The linter owns only what a parser can decide: presence, format, uniqueness, resolvable references, canonical markers. Everything requiring judgment — evidence quality, QAS feasibility and trade-offs, scope coherence, metric hygiene — stays in the skills' rubric/critic gates. The two result sets are always reported separately, never merged into one verdict.

**Invocation.** Every artifact-producing skill runs the applicable checks at finalize; applicable failures block finalize — except that a legitimately unresolved field carrying a canonical open marker (below) passes the check while staying visible in the report. CI or pre-commit hook integration is optional, never required.

**Canonical open-marker syntax.** No such convention existed anywhere in the method docs or ledgers, so this plan defines it: a field is *explicitly open* when its value starts with the literal token `OPEN:` followed by what is needed to resolve it — e.g. `Verification: OPEN: needs a decision on the load-test rig`. This is the single spine-wide convention; every skill writes it and the linter parses it. Any other placeholder (`TBD`, `???`, an empty value) fails LNT-05, so a proposal or gap can never pass as a completed value.

**QAS field labels.** The six-part scenario's sixth part is named *response measure* in prose, but the parseable field label — per the labeled example block in [quality_attributes.md](../quality_attributes.md) — is `Measure:`. The linter parses the labels `Source:/Stimulus:/Environment:/Artifact:/Response:/Measure:`; "response measure" stays the prose name for the `Measure:` field, and skills emit the labels verbatim.

**Bundle-review ID decision.** The companion's local judgment IDs (its `decisions.md` rows) get their own `BRV#` family (*bundle review*), recorded in the companion's Phase 0 ID inventory as companion-owned, so LNT-02 can mechanically separate them from the loop's reserved `DEC#`. The name is confirmable at authoring; the mechanical-distinguishability requirement is not.

### 3.2 External-dependency policy

Normative for every external reuse in this skillset. Each contribution-ledger row's reuse mode resolves to exactly one of the three modes below; the mode determines the provenance record it must carry and the runtime behavior it permits. The §3.1 call-contract table is the instance of the `call` rule; the ledgers' distill and pattern rows are the instances of the other two.

**`call` — version-pinned invocation.** A callable dependency needs all four of:

1. *Version-pinned install.* For an **external repository**: the exact commit or release, recorded in the skillset dependency manifest at authoring — never a floating branch or tag; upgrades happen only via a ledger-row reopen. For a **local skill**: the skill name plus its version/commit in the skills repo, recorded at authoring; a contract change reopens the governing ledger row.
2. *Bounded contract.* Named callers, invocation condition, inputs, and outputs (the §3.1 table columns).
3. *Explicit fallback.* An unavailable callee never blocks the stage and never yields fabricated output.
4. *No ownership of spine artifacts.* A callee never owns, writes, or mutates the companion bundle or loop workspace; the calling skill records the output.

**`distill` — vendored content with full provenance.** Distilled material is vendored with the skillset — never fetched at runtime — and every vendored item carries: source repository and exact file path; commit/tag or retrieval date; license; and attribution. Per the distill-provenance digest, all **15 distill rows** across the seven ledgers (`discover-product` 9 — DP-001..DP-007 pure, DP-012/DP-019 hybrid; `define-release` 5 — DR-EXT-01..05; `specify-requirements` 1 — SR-EXT-08) are currently provenance-incomplete and **nothing is vendored yet**. Donor audit and provenance capture are therefore an explicit **authoring-time obligation on every distill row**: inspect the exact donor files at a pinned revision, record per-candidate dispositions and the destination skill file/section, and vendor adopted material with the four provenance fields — before any distilled text lands in a skill. The per-row authoring-time donor-audit task list for all 15 rows is in §3.3. Two pinned donor snapshots cover the distill surface: `huntsyea/product-skills` and `assimovt/productskills` (both MIT) back nearly all 15 rows. DR-EXT-01 and SR-EXT-08 consume the same huntsyea story-mapping donor and share one provenance record at one pinned revision (a divergence must be recorded and reconciled in both ledgers); DR-EXT-01's provenance must additionally record that donor's former `rohanpatriot` location.

**`pattern` — local implementation, inspiration recorded.** The mechanism is independently authored with zero copied text; the inspiring source is recorded with repository, license, and retrieval date; there is no runtime dependency on the source. The per-skill source/dependency manifests are the realizing record of this policy.

**Hard rules.**

- **No runtime fetch.** No skill ever fetches a third-party repository at runtime (see also §3.1's routing exclusions).
- **No license-incompatible distillation.** `deanpeters/Product-Manager-Skills` (CC BY-NC-SA) is never distilled or copied — pattern/reference-only in every ledger. `florianbonnet14/ThePowerOfAnalytics_ClaudeSkills` has no stated license → pattern/reference-only. The loop's exit criterion is the [readiness-for-design checklist](../overview.md#readiness-for-software-design): the skillset is done with a topic when those questions are answerable. What happens next (design, implementation) is outside this plan; `validate-release` re-enters from post-release evidence whenever it arrives.

Entry points other than greenfield (per [lifecycle tailoring](../lifecycle_tailoring.md)) skip forward: *new capability* enters at `discover-product`; *rework* enters at `validate-release` evidence; *compliance mandate* enters at `specify-requirements` with the mandate as a constraint; *fast-follow* enters at `define-release`.

**Discovery pivot vs. vision pivot (skillset-wide definitions).** Every adaptation the loop makes is one of exactly two kinds, and each skill's routing names which:

- A **discovery pivot** is routine discovery/validation adaptation under a stable vision: changed opportunities, solutions, scope, or strategy — including reordering the vision's thin ordered-outcomes strategy section (§2's representation decision). It is the normal case; it must never silently edit the vision. Every §4.2 route except condition 8 is a discovery pivot.
- A **vision pivot** revises the intended future itself. Only `brainstorm-vision` and `create-vision-companion` may make one, and only through an explicit loop `DEC#` citing evidence that invalidates the intended future or target need (§4.2 condition 8; RTS-12). A failed experiment or weak feature is refused as pivot grounds and rerouted downstream as a discovery pivot (RTS-11). `brainstorm-vision` *cites* that loop `DEC#`; it never writes one (its no-loop-ID rule, §5.1), and the companion never edits the vision at all — it routes (§5.2).

Routine findings therefore always route to opportunities, solutions, scope, or strategy first; the vision route is the rare exception, evidence-gated, `DEC#`-gated, and owned by the two vision skills alone.

### 4.1 Handover contract (skillset-wide)

Every skill in the §3 table ends a successful run with a **handover** carrying exactly these five fields. The per-skill handover bullets in §5 instantiate this contract — they name which concrete values fill each field for that skill — and none may weaken it. Regression axis 4 (§6) scores it on every run.

1. **Next applicable stage** — selected from `lifecycle-onepager.md` (entry point plus selected stages, honoring recorded skips), never from a hard-coded stage order.
2. **Changed artifacts** — the exact file paths and IDs created or modified in this run.
3. **Unresolved decisions** — the open `DEC#` entries and `OPEN:`-marked fields the next stage inherits.
4. **Progression gate** — what must be true before the next stage may run: the finalize checks passed, the applicable §2.2 linter results, and any required human confirmations.
5. **Recorded skips** — every intentionally skipped stage the handover passes over is named with the reason recorded in the one-pager; a silent skip is a blind spot and fails regression scenario RTS-02.

**Chaining guardrail.** Command chaining — one skill's handover directly invoking the next — must not override lifecycle tailoring. The mechanism is explicit: the invoked skill re-reads `lifecycle-onepager.md` at start and re-derives the applicable next stage itself; when a chained instruction contradicts the one-pager (a skipped-in stage, a bypassed gate, a roadmap demanded that the one-pager records as skipped), the one-pager wins and the conflict is resolved by the out-of-order rule below. Existing evidence hooks: RTS-02 (a chained handover must respect a recorded skip) and RTS-13 (chaining into `define-release` must not demand or drop the roadmap against the one-pager's adopt/skip record); no new scenarios are needed.

**Out-of-order execution — decided: refuse silent violations; warn-and-record legitimate recorded deviations.** This resolves the question left open in §8 (item 7) and flagged by the `tailor-lifecycle` ledger. A skill invoked out of the tailored order **refuses to run** when proceeding would violate the one-pager's tailoring record or an unmet progression gate *without* a recorded reason — e.g. chaining straight to `specify-requirements` while `define-release` is neither completed nor recorded as skipped. It **warns and records** — proceeding with the deviation named in its handover and, when consequential, a `DEC#` — when the deviation is a recorded intentional skip, a re-entry per §4.2, or a reason the human states and the skill records on the spot (recording converts a silent violation into a legitimate one; refusal is therefore always escapable, never silently). Rationale: a warn-only rule would let command chaining nullify the one-pager, and the ledger requires the implemented behavior to be explicit and tested; a refuse-everything rule would fight the method's own re-entry model and the low-ceremony principle (design principle 5). The one-pager guides, recorded human judgment overrides, silence never does.

### 4.2 Re-entry definition (skillset-wide)

Re-entry — reopening an earlier artifact and resuming the loop there, per the §4 diagram — is always a **route**, never a generic "revisit earlier work". Every route carries six fields (enforced for reviews by LNT-17): the exact reopened artifact IDs, one named accountable owner, the preserved (non-reopened) decisions, the required new evidence, urgency, and a closure condition. Perseverance — reopening nothing — is recorded with its rationale just as reopening is. A route in flight is a legitimate deviation under §4.1's out-of-order rule (warn-and-record, not refuse).

The `validate-release` backtracking conditions map to routes as follows (§5.7 instantiates this table and adds the verdict/urgency fields at review time):

| # | Post-release finding | Artifact reopened | Skill re-entered |
| --- | --- | --- | --- |
| 1 | Capability used, outcome unmoved | Opportunity selection / `REL` scope (`OPP#`, `CAP#`) | `define-release` |
| 2 | Capability barely used | Value assumption (`ASM#`/`OPP#`) | `discover-product` |
| 3 | Misuse or workarounds | Journey/usability assumption (`UC#`) | `discover-product` and/or `specify-requirements` |
| 4 | Guardrail breached | Lowest challenged artifact: `REL` scope, `REQ#`, `QAS#` — a vision principle only via condition 8 | `define-release` / `specify-requirements` |
| 5 | Incident, support burden, poor recovery, degraded mode | `QAS#` and related `REQ#` | `specify-requirements` |

Independent multi-critic reviews use companion-specific rubrics (no imported NFR content).

### 5.3 `tailor-lifecycle` (new)

- **Mode:** short interview — adaptive depth: a compact component-selecting workflow that asks only enough to resolve entry point, ceremony, cadence, artifacts, authority, and revisit trigger, staying within a 10–15-question target for low-risk topics and deepening only on risk or ambiguity, with the reason recorded. Output is one file.
- **Does:** classify the topic (greenfield / new capability / rework / mandate / fast-follow / platform), size ceremony per driver, select which loop skills and artifacts this topic uses, set cadence and decision owners. Writes `lifecycle-onepager.md` — the sole output; canonical method terminology throughout; no donor workspace, taxonomy, or stage-artifact scheme.
- **Key behavior:** the minimum-ceremony package is the default path for low-risk solo work — full ceremony is never the default; stages and artifacts are recommended only when they reduce an important uncertainty or improve a consequential decision (completeness-driven selection is a guarded failure mode); every known stage not selected is explicitly recorded as skipped with a reason ("a silent skip is a blind spot"), and finalize fails when a stage is neither selected nor explicitly skipped. Other loop skills read `lifecycle-onepager.md` at start and respect it.
- **Roadmap ceremony gate:** the one-pager records **adopt** or **skip** for the optional roadmap, with the deciding driver — coordination cost, sponsor communication, or product lifetime. Adoption hands the maintenance obligation to `define-release`; skip means the strategy list and decision log are sufficient and no downstream skill may demand a roadmap. LNT-14 is armed only for adoption, and RTS-13 exercises both variants.
- **Handover:** every successful run ends by naming the selected entry skill, the later enabled stages, the reason, and the required input artifact — the next stage is derived from entry point plus selected stages, not a hard-coded order (rework → validation evidence, mandate → requirements, fast-follow → definition). This is the producing end of the §4.1 handover contract: the one-pager this skill writes is the record from which every later handover derives its next-applicable-stage field, the record the §4.1 chaining guardrail defends against command chaining, and the record whose silent violation the §4.1 out-of-order rule refuses — while recorded skips and §4.2 re-entries proceed as warn-and-record.
- **Revisit trigger:** the one-pager's revisit trigger is a set of concrete evidence conditions, each naming which tailoring decision is reconsidered — never "revisit when needed". Each trigger is a §4.2 re-entry route into `tailor-lifecycle` itself: the reopened artifact is `lifecycle-onepager.md`, and the closure condition is a re-tailored one-pager that downstream skills then follow.
- **Ownership gate — the seven-field decision-authority record:** the one-pager's decision-authority section records, for every consequential decision type and selected stage, all seven ownership fields from [collaboration_and_decision_ownership.md](../collaboration_and_decision_ownership.md): (1) exactly **one named accountable owner** — a group, trio, or department is never an accountable owner and is rejected at finalize (RTS-07); (2) **required contributors**; (3) **specialist authorities**; (4) **formal approvers**, where a contractual, regulatory, funding, or governance process requires them (approval never replaces the accountable owner); (5) the **evidence required to decide**; (6) the **escalation path**; (7) the **evidence-based reopen trigger** — which feeds the revisit triggers. A legitimately unresolved field carries a canonical `OPEN:` marker (LNT-05); finalize blocks on a missing field or a group-only owner. The tailoring interview includes a **specialist-participation question**: which specialist evidence — engineering, design, operations, security, compliance, domain, or other — is material for this topic; the answers become the named required contributors and specialist authorities that downstream skills gate on (RTS-08). Role names from the method doc's default ownership matrix are replaced with actual people; in a small team one person may hold several roles, but the roles are recorded separately so missing perspectives stay visible. Design and architecture decisions stay under engineering/architecture authority — the future design skillset's territory (§7) — never product-management authority by default. This one-pager record is the single source every downstream ownership gate reads (`DEC#` owners in §5.4, `REL` decision metadata in §5.5, requirements human-gate owners in §5.6, review/re-entry owners in §5.7); a handover crossing a decision-authority boundary without the named owner and escalation path from this record is refused (RTS-09). These rules live in the existing skills and the one-pager itself — no standalone ownership skill and no additional mandatory runtime document.
- **Provenance:** runtime calls pinned, distilled material carries full provenance, no donor repo is ever fetched at runtime — the external-dependency policy (§3.2) is the normative statement of these rules; the ledger's focused donor-audit manifest (six repos) is an authoring-time task under §3.2's distill obligation.
- **Finalize:** runs the deterministic linter (§2.2) — LNT-05 and LNT-13 on the one-pager — reported strictly separately from the judgment review; applicable failures block except under the open-marker policy; its roadmap adopt/skip record arms LNT-14 for `define-release` only when the roadmap is adopted. The judgment rubric runs all **eight** completion checks from [lifecycle_tailoring.md](../lifecycle_tailoring.md): (1) entry point matches uncertainty; (2) skips are recorded with reasons; (3) roadmap adoption or skip is explicit and justified by coordination cost, sponsor communication, or product lifetime; (4) ceremony matches risk, irreversibility, and regulation per driver; (5) one cycle has a defined decision output; (6) every consequential decision type has one named owner and an escalation path; (7) contributors, specialist authorities, and approvers are named where applicable; and (8) a revisit trigger exists. RTS-13 exercises both roadmap variants, and the adopted variant arms LNT-14; this is the existing roadmap gate, not an additional completion check.
- **Regression hooks:** scenarios RTS-01 (low ceremony), RTS-02 (recorded skip), and RTS-13 (roadmap adopt/skip) of the reference-topic rubric (§6) exercise this skill's gates; the skill runs inside the scored end-to-end reference-topic run.

### 5.4 `discover-product` (new)

- **Mode:** interview for evidence and judgment; light derive for restructuring maps.
- **Does:** the [discovery loop](../product_discovery.md#discovery-loop) — frame the outcome; coach the human through evidence capture (`EV#` — the agent asks about *specific past behavior*, never accepts hypothetical enthusiasm as strong evidence); map opportunities (`OPP#`) separately from solutions; **generate alternatives** (`SOL#`) — ≥3 materially different solution directions for the targeted opportunity, including process, policy, manual-service, and no-build options where plausible, or an explicit `DEC#` recording why alternatives are not viable, recorded in `solutions.md` with rejected/parked directions retained and reasoned; expose and rank assumptions (`ASM#`) by the four risks, each citing the `SOL#` it belongs to (or `OPP#` only when solution-independent); draft experiment cards (`EXP#`) per the merged schema below — explicit assumption/hypothesis content plus predeclared support/refute/inconclusive criteria, each card citing its target `ASM#` and the applicable `SOL#`; record the proceed/adapt/pause/abandon decision (`DEC#`).
- **Distilled technique base.** The skill's reference sub-files vendor distilled techniques and anti-patterns — the seven-step loop's techniques and phase anti-patterns (huntsyea `continuous-discovery`), the optional JTBD switch-interview/forces lens routed only for motivation/switching uncertainty, and the cheapest-trustworthy-test method selection across all four risks (prototype, concierge/Wizard-of-Oz, spike, data analysis, demand test, policy/security/legal review, pilot). Every relevant anti-pattern maps to a guardrail, finalize check, or explicit rejection in an anti-pattern coverage table. All distills are audit-conditioned: the ledger's donor-audit manifest (repo, path, pinned revision, retrieval date, license, attribution) is an authoring-time task; nothing is vendored yet. Premature-convergence coaching is authored independently — reference-only, no Dean Peters text.
- **Evidence quality.** Interview guardrails ask for concrete recent behavior (Mom-Test style) and classify opinions/hypotheticals as weak; the problem-validation rubric (frequency / intensity / willingness-to-pay or a justified substitute) is applied without treating it as universal; every interview-derived `EV#` is classified Rich/Mixed/Thin, and confidence is capped by evidence quality — three Thin items never mechanically become Rich; exceeding the ceiling requires an explicit `DEC#` (LNT-18).
- **Opportunity routing and the human gate.** Every evidence-derived opportunity gets a routing decision — add / merge / escalate / park — with provenance preserved on merge and reasons on park/escalate; a human gate precedes solution generation: evidence is never silently converted into solutions, and AFK-produced proposals are marked *awaiting review*.
- **Integrations:** seeds from the companion's `discovery-seeds.md` and the vision's critical-assumptions stub; "test cheaply" may hand off to `prototype`, and contested domain language triggers `domain-modeling` — both per the §3.1 call contracts with explicit fallbacks; pause/resume via the `brainstorm-vision` `.wip` pattern; all `EV/OPP/SOL/ASM/EXP/DEC` records stay discoverable via the workspace index (LNT-04); a separated critic may review derived maps/cards — it gets artifacts and rules, never builder expectations.
- **Guardrail:** the skill *coaches* evidence-gathering, it never fabricates evidence. An `EV` row without a human-supplied source is invalid; missing evidence stays an explicit gap.
- **Guardrail — alternative-count refusal:** the skill refuses to *rank* solution assumptions while fewer than three materially different solution directions are on the table, unless a `DEC#` records why alternatives are not viable — the refusal fires at ranking time, not only at finalize. The wrap-up gate additionally re-runs the method doc's completion check *alternative solutions were considered*. Regression scenario RTS-04 (§6) exercises the single-solution case below this threshold — ranking refused without the `DEC#`, permitted with it — and scores the completion check.
- **Guardrails — discipline:** architecture-changing quality risks surface early as *classified assumptions*, explicitly not `QAS#`; no donor IDs, folders, or taxonomies enter the workspace — one proprietary spine; decision thresholds are predeclared so research ends (endless research cannot complete without thresholds or an explicit open decision).
- **Experiment-card schema.** Every `EXP#` card is the [method doc's complete experiment-card template](../product_discovery.md#experiment-card) merged with the spine — eleven fields: **decision to inform** (what decision this evidence informs), **assumption/hypothesis** (the explicit content under the method card's `## Assumption`, not merely an `ASM#` citation), **target `ASM#`**, **applicable `SOL#`** (the update-1 citation duty, a schema field here), **evidence needed** (what must be observed), **method** (the cheapest trustworthy test), **time budget** (research ends — pairs with the thresholds above), **predeclared support/refute/inconclusive criteria** (written before the test runs, never post-hoc), **result**, **confidence per relevant risk dimension** (value/usability/feasibility/viability — only the dimensions the target `ASM#` is classified under), and **resulting `DEC#`** (the proceed/adapt/pause/abandon entry the result fed). The first eight are required-resolved when the card is finalized; a missing or `OPEN:` assumption/hypothesis fails LNT-19. Result, per-risk confidence, and resulting `DEC#` may carry `OPEN:` markers until the experiment has run (LNT-19; citation integrity via LNT-03/LNT-07). The `prototype` call contract (§3.1) passes and returns exactly these fields.
- **Wrap-up and backtracking:** the wrap-up names the proceed/adapt/pause/abandon verdict, the next lifecycle stage from the one-pager, and the exact input artifacts; an *adapt* verdict becomes an explicit reopen instruction naming the affected `SOL#`/`ASM#`, never an indiscriminate restart. The wrap-up instantiates the §4.1 handover contract — the next applicable stage per the one-pager, the changed artifacts (the discovery files and `EV/OPP/SOL/ASM/EXP/DEC` IDs touched), the unresolved decisions (open `ASM#`/`EXP#` items and `OPEN:`-marked card fields), the progression gate (the wrap-up completion checks plus the linter set below), and any recorded skip passed over — and an *adapt* reopen is a §4.2 route: exact IDs, one named owner, preserved decisions, required new evidence, and a closure condition.
- **Discovery-pivot vs. vision-pivot routing:** every adapt decision is a §4 **discovery pivot** within the stable vision — `discover-product` never edits the vision. When evidence appears to invalidate the intended future or target need, the wrap-up routes a **vision re-entry recommendation** to `brainstorm-vision` via an explicit `DEC#` citing that evidence (the §4 vision-pivot gate); a failed `EXP#` or weak feature proposed as vision-rewrite grounds is refused at wrap-up and rerouted to opportunities, solutions, scope, or strategy (RTS-11; the genuine case is RTS-12).
- **Opportunity selection vs. strategy:** opportunity selection (the routing/targeting decisions above) is checked against the vision's thin ordered-outcomes strategy section, read from the companion's derived strategy index; selecting against the recorded order needs an explicit `DEC#` — never a silent divergence and never a silent reorder. Reordering the strategy itself is a §4 discovery pivot: recorded as a `DEC#` and applied to the vision one-pager's strategy section by its accountable human owner (no vision pivot, no `brainstorm-vision` reopen — the skill recommends, the human edits), after which the companion's derived strategy index is refreshed; it is never a companion edit.
- **Decision ownership and specialist participation:** the owner field of every proceed/adapt/pause/abandon `DEC#` names the one accountable individual recorded in `lifecycle-onepager.md`'s decision-authority section (§5.3) — a group, trio, or department as owner is refused (RTS-07). When a decision's feasibility, viability, or quality evidence is material, actual specialist input — engineering, design, operations, security, compliance, domain — is required per the one-pager's named specialist authorities; the skill never fabricates specialist evidence (extending the classified-assumption discipline and evidence non-fabrication above): the missing input stays an explicit `OPEN:` gap and the decision is refused until the input is supplied or the accountable owner records the gap in the `DEC#` (RTS-08).
- **Finalize runs the deterministic linter (§2.2):** LNT-01, LNT-03–LNT-07, LNT-18, LNT-19 on the discovery artifacts — including the `EV#` human-supplied source/date/strength rule (LNT-06), the full `SOL` chain (LNT-07), the evidence-confidence cap (LNT-18), and all eleven experiment-card fields per the merged schema, with a missing or unresolved assumption/hypothesis rejected (LNT-19); the wrap-up gate's judgment checks stay separate. A blind reference-topic run scores the skill against its completion checks (§6).

### 5.5 `define-release` (new)

- **Mode:** interview — selection and prioritization are human judgment; the agent enforces the discipline.
- **Does:** [product definition](../product_definition.md)'s activities — select `OPP`s (record deferrals with reasons); express scope as capabilities in solution-neutral language (reusing/extending the companion's `CAP` map); check the boundary against the vision's `S`-ladder and escalate to a vision conversation when scope fights it; prioritize with the stated criteria (every "must" needs a consequence; ties break by learning value); cut a thin coherent slice and name the hypothesis it tests, with success/guardrail/stop criteria. Writes `releases/REL<n>-definition.md`.
- **Journey shaping and slice discipline.** A progressive-disclosure story-mapping reference (distilled from the MIT huntsyea donor; donor audit with pinned revision, retrieval date, and attribution is an authoring-time task) supports shaping journeys and cutting the slice: a slice must span the end-to-end journey — a single-layer slice is rejected — or the one-pager records a deliberate story-mapping skip. Scope-cutting prompts and a finalize failure check distinguish *small* from *coherent*: a slice of disconnected items fails finalization.
- **Proportional ceremony.** An optional shaping/appetite path is ceremony-gated: appetite and commitment discipline are recorded *inside* the `REL` artifact, never a separate pitch artifact; a proportional-investment (bet-sizing) check ties investment to uncertainty, reversibility, and learning value, complementing the release stop criteria — a reversible uncertainty gets a smaller bet than an irreversible regulated commitment.
- **Mandatory-scope classification.** Every mandatory scope driver is classified Obligation / Expectation / Hope, and each obligation records the consequence that makes it mandatory — no `CP/CN/FR` identifiers; enforced deterministically by LNT-15 and consumed downstream by `specify-requirements` (LNT-16).
- **Hypothesis quality.** The `REL` hypothesis section predeclares how the release will be judged after shipping — success/failure/inconclusive interpretation, confidence per risk dimension, time budget, and investment boundary — so the release is judgeable without post-hoc criteria invention. This mirrors the merged `EXP#` schema's predeclared-criteria discipline (§5.4): a release is a bigger experiment, and its interpretation criteria, per-risk confidence, and time budget are written before shipping just as an experiment card's support/refute/inconclusive criteria and budget are written before the test runs; `validate-release` later holds the review to exactly these precommitted criteria (LNT-08, LNT-17).
- **Metric audit.** When outcome-metric hygiene is material, the release's success measures go through the version-pinned `north-star` callable specialist per the §3.1 contract (audit result or justified skip recorded in `REL` review metadata; local-review fallback); locally authored metric-tree prompts (MIT phuryn material, adapted) prepare candidate outcome/driver/input decompositions for that audit — never a second runtime dependency.
- **Guardrails:** refuses a release without a hypothesis or stop criteria; refuses scope items that trace to no `OPP`/evidence without an explicit `DEC` override — every scope decision resolves to evidence or carries the override.
- **Handover and backtracking:** the final response names the next stage selected by `lifecycle-onepager.md`, all required input files, unresolved blockers, and the resume point — `specify-requirements` must be able to start without rediscovering state; a backtracking-trigger matrix (pattern-only local implementation — the ForceInjection donor license is WIP/unverified, so nothing is copied) maps each trigger to one artifact, decision owner, and next skill: back to discovery, a vision re-entry request, domain work, or stopping definition; an ambiguous "go back" fails review. The final response instantiates the §4.1 handover contract — the next stage per the one-pager, the changed artifacts (`REL<n>-definition.md` and the `REL#`/`CAP#` records), the unresolved decisions (the named blockers and open `DEC#` items `specify-requirements` inherits), the progression gate (the guardrails above plus the linter set below), and any recorded skip passed over. The trigger matrix's rows are §4.2 routes (one artifact, one owner, next skill, closure condition), and the post-release conditions that reopen a release land here through the §4.2 condition map (conditions 1, 4, and 6 route to `define-release`). The matrix's vision trigger is sharpened by the §4 pivot definitions: **a vision-boundary conflict routes to a vision re-entry request — an explicit `DEC#`-carrying route to `brainstorm-vision` — never a vision edit or a silent scope expansion**; `define-release` makes discovery pivots only (back to discovery, scope, or strategy), and a failed release or weak feature offered as vision-rewrite grounds is refused and rerouted (RTS-11; the genuine `DEC#`-gated case is RTS-12).
- **Opportunity selection vs. strategy:** the selection step checks the chosen `OPP`s against the vision's thin ordered-outcomes strategy section, read from the companion's derived strategy index: a selection that fights the recorded order needs a strategy conversation and an explicit `DEC#` — a recorded discovery pivot reordering the strategy section, or a recorded exception — never a silent reorder, a silent divergence, or a vision edit.
- **Ceremony-gated roadmap maintenance:** only when `lifecycle-onepager.md` records roadmap adoption (the `tailor-lifecycle` decision, driven by coordination cost, sponsor communication, and product lifetime — §5.3, arming LNT-14) does `define-release` maintain the **outcome-based rolling now/next/later view**: each entry names an outcome (feature-only or date-only entries fail LNT-14), *now* mirrors the committed `REL` slice, *next/later* mirror the strategy section's remaining ordered outcomes, and the view is revised as evidence arrives — never committed features-and-dates. A skipped-roadmap topic produces no roadmap and nothing downstream may demand one (RTS-13 scores both variants).
- **Decision-metadata ownership and specialist participation:** the `REL`'s decision metadata (the owner/date/review fields LNT-15 checks) carries §5.3's full seven-field depth for the release commitment, per `lifecycle-onepager.md`: one named accountable owner — a group or department as owner fails finalize (RTS-07) — plus required contributors, specialist authorities, formal approvers where applicable, the evidence required to decide, the escalation path, and the evidence-based reopen trigger. When usability, feasibility, viability, or quality evidence is material to scope, the named design/engineering/operations/security/compliance/domain input is present before the release finalizes — a missing required specialist input blocks finalize or is recorded as an explicit `DEC#` skip with the gap carrying an `OPEN:` marker (RTS-08); the skill fabricates no specialist evidence.
- **Finalize runs the deterministic linter (§2.2):** LNT-01, LNT-03–LNT-05, LNT-08 (hypothesis + success/guardrail/stop criteria), LNT-09 (an instrumentation/observation requirement per outcome and guardrail criterion), LNT-15 (O/E/H classification, capability→opportunity/evidence resolution, deferral reasons, decision owner/date/review fields), and — when the one-pager records roadmap adoption — LNT-14.

### 5.6 `specify-requirements` (new)

- **Mode:** AFK derive with a human review gate (the companion's builder/critic + `decisions.md` pattern, at smaller scale) — most content is restructuring the committed slice; conflicts and gaps go to the human.
- **Does:** for one `REL`: elaborate the in-scope `UC`s with alternative and failure paths ([use cases doc](../use_cases_and_story_mapping.md)); specify functional/interface/data/transition requirements (`REQ#`) in the trigger–response–constraint form from [requirements_engineering.md](../requirements_engineering.md); sharpen quality attributes into measurable scenarios (`QAS#`), seeding from the `*-architecture-lens.md`; maintain traceability `EV/OPP → SOL → CAP → UC/REQ/QAS` (the discovery-side chain `OPP → SOL → ASM → EXP` is owned by `discover-product`, §5.4).
- **Fresh-critic protocol.** The requirements critic runs in a separate context receiving the authoritative input artifacts, candidate outputs, schemas, gates, and lint results — never builder reasoning or expected verdicts; seeded plausible errors must be detected, and the verdict stays stable when builder rationale is withheld.
- **Durable-workspace discipline.** Rejected and unresolved alternatives are preserved as durable artifacts; indexes and handover lists must match the files actually present (LNT-04) — stale indexes and missing rejected alternatives fail validation.
- **Slice boundary contract.** The committed story-map slice from `define-release` is the authoritative boundary: UC elaboration surfaces unresolved alternative/failure paths *without* recreating or expanding release scope; out-of-scope `REQ`/`QAS` need an explicit change `DEC#` (LNT-16).
- **Trace rationale.** The shared linter (the Adapt of Problem-Based-SRS's mechanical validation — no `.spec` JSON, no `CP/CN/FR` IDs) enforces the chain; every `REQ`/`QAS` additionally traces to a need, risk, constraint, or obligation with its rationale, consuming the O/E/H classification from the `REL` (LNT-16).
- **QAS elicitation and gate.** ISO 25010-flavoured completeness prompts cover operational and stakeholder consequences without checklist inflation (no Obsidian schemas/tags/vault layout — donor license unverified, pattern-only); each critical QAS records the three gate dimensions **Complete / Measurable / Feasible** — independent review separation is mandatory, multi-agent fan-out optional; QAS drafting may conditionally call the `quality-attribute-scenario-writer` specialist per the §3.1 contract (depth-audit condition, pin, local-drafting fallback), with every candidate passing this same gate before a `QAS#` exists.
- **Integrations:** calls `domain-modeling` when new terms/rules surface (`domain-glossary.md` and `CONTEXT.md` stay canonical; §3.1 call contract); `grill-with-docs` as the validation review. Its output — the specified slice — is this skillset's terminal artifact; what consumes it is the future design skillset's concern (§7).
- **Guardrails:** flags vague terms ("fast", "secure") without measurable criteria; every `REQ` needs a verification method or an explicit open marker (canonical `OPEN:` syntax, §2.2); invented paths, targets, terms, or rules are marked as proposals requiring confirmation — a proposal can never pass as a completed value (LNT-05).
- **Handover and backtracking:** the final output names the design-readiness status, exact artifacts, open questions, required human confirmations, validation hooks, and the next workflow selected by tailoring; failed gates route to a named target — back to `define-release`, `discover-product`, `domain-modeling`, or human confirmation — instead of forcing completion, each route naming the target artifact and owner. The final output instantiates the §4.1 handover contract — the design-readiness status is the progression gate (the readiness-for-design checklist plus the linter set below), the exact artifacts are the changed set, the open questions and required human confirmations are the unresolved decisions the next stage inherits, the next workflow comes from the one-pager, and any recorded skip passed over is named. Each failed-gate route is a §4.2 route, and §4.2's post-release conditions 3, 5, 6, and 10 re-enter the loop at this skill.
- **Singular accountable ownership and specialist verdicts:** every consequential requirements decision the human gate resolves — invented failure paths, target values, domain rules, scope changes, consequential trade-offs — is recorded in its `DEC#` with the one named accountable owner from `lifecycle-onepager.md`'s decision-authority record (§5.3); a group or department as owner is refused (RTS-07), and the handover lists unresolved decisions with their owners. The QAS gate's **Feasible** dimension passes only on a recorded engineering/domain/operations/security reviewer verdict or a blocking-uncertainty `OPEN:` marker escalated to the human gate — never auto-passed (RTS-08). The builder must not fabricate specialist evidence: invented stakeholder judgment, domain rules, failure behavior, or measurable targets stay flagged proposals that cannot pass as completed values (LNT-05), and the critic checks for unmarked invention. Each failed-gate route carries the owner and escalation path from the one-pager, and the skill refuses to elaborate a `REL` slice whose upstream `OPP`/`ASM`/`REL` has been invalidated unless perseverance is recorded with its rationale as a `DEC#` (RTS-10).
- **Finalize runs the deterministic linter (§2.2):** LNT-01, LNT-03–LNT-05, LNT-10 (`REQ` verification method or open marker), LNT-11 (`QAS` six fields, open markers, measurable `Measure:`), LNT-12 (transition requirements for retired scope), LNT-16 (trace rationale and scope boundary); the human review gate's judgment findings stay separate.

### 5.7 `validate-release` (new)

- **Mode:** short interview per review cadence.
- **Analysis-planning gate.** Before any result is inspected, the skill writes a durable, timestamped analysis plan into `validation/REL<n>-review.md` — review question and decision owner, the unchanged precommitted criteria, metric definitions (outcome vs driver vs input vs usage vs guardrail), population/segments/time window, qualitative and operational evidence sources, quality limitations, confounders, evidence-strength rules, and the persevere/adapt/pause/retire decision rules. Any post-hoc plan change is a dated `DEC#` with the original visible (LNT-17). Independently authored mechanism — the inspiring repository has no stated license, so nothing is copied.
- **Does:** compare observed outcomes against `REL`'s success/guardrail/stop criteria; pull in evidence accumulated via `qa`/`triage` issues (§3.1 call contract — source-addressable observations only, with the manual-intake fallback); record the verdict and — the essential part — **what it reopens** (vision / opportunities / scope / requirements) as `DEC` entries plus new `EV` rows, then point at the loop re-entry. Post-release `EV#` rows use the shared Rich/Mixed/Thin strength model with the source-quality confidence cap — volume never inflates confidence (LNT-18).
- **Metric audit.** When outcome-metric hygiene is material, the review runs the version-pinned `north-star` specialist per the §3.1 contract — vanity-metric refusal, driver/input decomposition — preserving result, warnings, or the justified skip in the review; locally authored metric-tree material (adapted from MIT phuryn sources) structures the local-fallback review; no second runtime dependency.
- **Context-separated verifier.** Where the review includes substantial derive work, evidence extraction is separated from verdict review: the verifier sees raw evidence, precommitted criteria, candidate findings, and gates — not the analyst's intended conclusion; confirmation-bias fixtures exercise this in §6.
- **Re-entry matrix and handover.** A re-entry/backtracking matrix — an independently authored pattern (the ForceInjection donor license is WIP/unverified, so nothing is copied) — routes each finding to the challenged decision, the reopened artifact, one owner, required evidence, the next skill, and a closure condition; generic "revisit earlier work" fails. The review ends with a handover naming the verdict, reopened artifacts with exact IDs, named owners, next skill, exact input files, urgency, and preserved (non-reopened) decisions; perseverance is recorded with rationale just as reopening is. The matrix's rows are exactly the ten-condition map in §4.2 — each post-release finding class routes to the artifact and skill reopened, including the `domain-modeling` external-call route (condition 7, per §3.1) and the measurement-repair non-route (condition 9) — and the closing handover instantiates §4.1 with the verdict and urgency added as this skill's route-level fields.
- **Vision-stability escalation guard:** the matrix's condition-8 route is the only path to the vision, and it is guarded by the §4 pivot definitions — **only evidence contradicting a foundational actor/outcome/value/principle/boundary assumption routes to the vision, via an explicit `DEC#` citing that invalidating evidence**; `validate-release` routes, it never edits the vision. Every other finding (conditions 1–7, 9, 10) is a discovery pivot reopening downstream artifacts — a finding explained by a lower-level opportunity, scope, journey, requirement, or `QAS` never escalates past it, and each route is labeled discovery pivot or vision pivot in the review. A failed release or failed experiment offered as vision-rewrite grounds is refused and rerouted downstream (RTS-11); the genuine foundational contradiction proceeds only with the `DEC#` (RTS-12, §4.2 condition 8).
- **Review and re-entry ownership; specialist evidence:** the analysis plan's decision owner and every re-entry route's owner are one named accountable individual per `lifecycle-onepager.md`'s decision-authority record (§5.3) — a team or department as owner fails the review or route (RTS-07). Findings in specialist territory — operational evidence, guardrail breaches, incidents, audit/compliance findings — require a source-addressable specialist `EV#` (via the `qa`/`triage` intake or the analysis plan's operational-evidence sources) or an explicit `OPEN:` marker; specialist evidence is never fabricated (RTS-08). A re-entry crossing a decision-authority boundary names the owner and escalation path from the one-pager (RTS-09), and no route is closed — and no dependent work continued — while its reopened artifact is unresolved, unless perseverance is recorded with its rationale as a `DEC#` (RTS-10).
- **Guardrail:** shipping is not success; a review that measures nothing but "it shipped" is flagged as such.
- **Runs the deterministic linter (§2.2) before routing findings:** LNT-01, LNT-03–LNT-05, LNT-17, LNT-18, so every reopened `REQ/QAS/CAP/OPP` reference resolves before re-entry and the downstream impact list is complete; it consumes LNT-09's guarantee — an outcome that cannot be observed yields measurement repair, never a fabricated verdict.
- **Regression hooks:** scenarios RTS-06 (post-release reopening), RTS-10 (invalidated upstream artifacts), RTS-11 (over-escalation refused), and RTS-12 (vision pivot with `DEC#`) of the reference-topic rubric (§6) exercise this skill's routing and refusal behavior.

## 6. Skillset regression validation

The deterministic linter (§2.2) guards the *artifacts*; this section guards the *skills*. One small **reference topic** — fixed, vendored with the skillset alongside its fixtures and scored run reports, never part of any real product workspace — is run end-to-end (greenfield entry: `tailor-lifecycle`, both vision skills, the loop, `validate-release`) **after each skill is authored or materially changed**. The run is blind: the executing agent gets the topic and the skills, never the expected outcomes; scoring compares the produced workspace and transcripts against the rubric below.

**Scoring axes.** Every run is scored on five axes, with deterministic and judgment results reported separately (§2.2 rule):

1. **Method-doc completion checks** — each skill's finalize gate re-runs its stage doc's completion checks per the §2.1 mapping; every check passes or leaves an explicit `OPEN:` stub.
2. **Ledger coverage gates** — the run exhibits the realizing mechanisms of the accepted rows in the seven per-skill contribution ledgers (the acceptance evidence named in this plan's header); deviations are recorded against the ledger row ID.
3. **Linter results** — a full LNT-01–LNT-19 sweep (§2.2) over the produced bundle + workspace at the end of the run, plus each skill's finalize check set from §5.
4. **Handover** — every skill's closing output carries the five §4.1 contract fields, naming the next applicable stage per `lifecycle-onepager.md` and the exact input artifacts; chaining never overrides tailoring (§4.1 guardrail).
5. **Re-entry** — reopened artifacts are cited with resolvable IDs (LNT-03), each reopen is a §4.2 route, and the loop re-enters at the reopened artifact per §4.

**Failure handling.** Every failed scenario or axis is recorded in the scored run report, attributed to the responsible skill — or to this plan when the design itself is at fault — and that skill or plan section is updated and the run repeated before the change is accepted.

**Scenarios.** Each scenario has a stable ID: ledger rows, later plan revisions, and authoring-time tests cite `RTS-xx` as objective evidence, so IDs are append-only — new scenarios get new IDs, and a retired scenario keeps its ID with a retirement note. Scenarios run as variants of, or seeded probes on, the one reference topic (two tailoring variants exist: low-ceremony and high-coordination).

| ID | Scenario | Pass condition |
| --- | --- | --- |
| RTS-01 | Low ceremony | The low-ceremony variant completes with the minimum package and explicit `OPEN:` stubs (LNT-05); no skill inflates ceremony beyond the one-pager (design principle 5); no roadmap is demanded. |
| RTS-02 | Intentionally skipped stage | The one-pager records the skipped stage with a reason (§5.3 — "a silent skip is a blind spot"); downstream skills respect the skip and hand over to the next *applicable* stage; a silent skip fails the run. |
| RTS-03 | Weak evidence | Seeded opinion/hypothetical input is classified as weak evidence (Rich/Mixed/Thin) and confidence stays capped by evidence quality (LNT-18); an `EV#` row without a human-supplied source, date, and strength fails LNT-06. |
| RTS-04 | Single-solution exception | The single-solution fixture is below the ≥3 materially different directions threshold: with only one `SOL#` direction on the table, `discover-product` refuses assumption ranking *at ranking time* (§5.4 guardrail); with a `DEC#` recording why alternatives are not viable, ranking proceeds and LNT-07's ≥3-directions-or-`DEC#` rule passes; the finalize check *alternative solutions were considered* is scored explicitly. |
| RTS-05 | Requirements gap needing human review | `specify-requirements` hits a gap only a human can settle (an invented failure path, an unsettled target value); the gap reaches the human review gate as an explicit `OPEN:` item (LNT-05, LNT-10, LNT-11), never a fabricated value. |
| RTS-06 | Post-release evidence reopens an earlier artifact | Evidence arriving via `qa`/`triage` challenges an earlier artifact; `validate-release` records the verdict and the reopened artifact with resolvable IDs (LNT-03), and re-entry per §4 lands on that artifact. |
| RTS-07 | Group-only owner — detect and refuse | A consequential decision offered with a team or department as its owner is refused: a group is not an accountable owner ([collaboration_and_decision_ownership.md](../collaboration_and_decision_ownership.md), mapped to all skills in §2.1). |
| RTS-08 | Missing specialist/engineering input — detect and refuse | A decision whose feasibility/viability/quality evidence is material proceeds without actual specialist input → refused; the skill fabricates no specialist evidence; the gap stays an explicit `OPEN:` marker. |
| RTS-09 | Department-boundary handoff — detect and refuse | A handover crossing a decision-authority boundary without the named accountable owner and escalation path from `lifecycle-onepager.md` is refused. |
| RTS-10 | Refusal to reopen invalidated upstream artifacts — detect and refuse | Evidence invalidates an upstream artifact; continuing dependent work without reopening it is refused, unless perseverance is recorded with its rationale as a `DEC#`. |
| RTS-11 | Failed experiment escalated to a vision rewrite — refuse and reroute | A failed `EXP#` proposed as grounds for rewriting the vision is refused and rerouted as a discovery pivot to opportunities, solutions, scope, or strategy; the vision file is untouched. |
| RTS-12 | Genuine vision-invalidating evidence | Evidence invalidating the intended future or target need reopens the vision only through an explicit `DEC#` citing that evidence; the vision pivot proceeds (reopen `brainstorm-vision`, refresh the companion) and the affected finalize checks rerun; without the `DEC#` the reopen is blocked. |
| RTS-13 | Roadmap ceremony gate — paired variants | Low-ceremony variant: the one-pager records the roadmap *skipped* with a reason and nothing downstream demands one. High-coordination variant: it records *adoption* and `define-release` maintains the outcome-based rolling now/next/later view; a feature-only or date-only entry fails LNT-14. |

The four detect-and-refuse scenarios (RTS-07–RTS-10) score the cross-cutting rules of [collaboration_and_decision_ownership.md](../collaboration_and_decision_ownership.md); RTS-11 and RTS-12 score the vision-stability discipline — routine findings are discovery pivots, a vision pivot is rare and `DEC#`-gated.

The per-skill fixture obligations from the ledgers feed this suite rather than duplicating it: the companion's 17-scenario end-to-end matrix and mutation tests, `discover-product`'s blind reference run and mutation set, `tailor-lifecycle`'s scored reference run, and `validate-release`'s blind-verifier / confirmation-bias fixtures all execute as part of, or alongside, the reference-topic run and are scored on the same five axes.
