# Skillset Plan: The Discovery–Definition–Requirements Loop

**Reading for authoring:** this document plus the one relevant stage method doc it links (the `../*.md` links).

**Packaging:** The seven skills ship as one plugin (`product-loop`), so the loop reads as a single skillset; skill names stay bare verb-noun at the call site.

## 1. Goal

Build a skillset/workflow that implements the **discovery–definition–requirements loop** from the [overview](../overview.md) as agent skills: the **lifecycle tailoring** entry step, the **product vision** anchor and the spine derived from it, the loop stages — **product discovery**, **product definition**, **requirements engineering** — and the **validation** re-entry, wired together by a stable ID scheme.

### Design principles

1. **Two skill modes, chosen per stage.** *Interview skills*, where the human supplies knowledge the agent cannot have — evidence, priorities, business judgment. *AFK derive skills* — an orchestrator with builder/critic sub-agents, a durable judgment log, and human review at the end — where the work is restructuring already-captured content. Discovery and definition are interview-heavy; specification and index maintenance are derive-heavy.
2. **The vision spine stays derived-only.** Loop artifacts live in a separate **loop workspace** and cite spine IDs; `<product>-vision-spine/` is never extended with loop content.
3. **One traceability spine, extended.** The spine's vision-side IDs (`S#`, `V#`, `UC#`, `BV#`, `INV#`, `CAP#`) are the anchor. The loop adds its own ID families (below) and every loop artifact cites upward: opportunity → outcome/vision, solution → opportunity, assumption → solution (or opportunity only when solution-independent), experiment → assumption + applicable solution, capability-in-scope → opportunity + evidence, requirement → capability/UC.
4. **Call other skills as loop steps.** `prototype` (discovery's "test cheaply"), `domain-modeling` (domain discovery), `grill-with-docs` (requirements validation), `qa` / `triage` (validation intake). This skillset's skills orchestrate around them, not replace them. Skills that belong to later phases (design, implementation planning) are *not* part of this skillset — see §7.
5. **Ceremony is tailored, not fixed.** The tailoring step decides which loop skills a topic actually runs; skills must degrade gracefully to a low-ceremony solo-developer setting ([minimum useful discovery package](../overview.md#minimum-useful-discovery-package)).
6. **The method docs in the parent folder are the skills' source material — all of them.** Each skill *must* consume its stage doc(s): templates become the skill's output shapes, completion checks become its finalize gates, failure modes become its guardrails. §2.1 maps every method document in the parent folder to its consuming skill so nothing is orphaned. **Mechanism — distill plus a vendored source trail.** No skill reads the method folder at runtime. Each consuming skill carries (a) distilled operational rules in its own sub-files and (b) a vendored source file holding the consumed excerpt with its source path, pinned revision, retrieval date, and doc status. A doc change is an explicit re-vendor diffed against the vendored copy, never a silent divergence (§3.3). Per §5.4's context strategy, sub-agents read the source files; orchestrators read the distilled rules.
7. **No artifact may share a name with a method doc.** Artifact names must differ from every method-doc name; the spine's ubiquitous-language file is therefore `domain-glossary.md`, distinct from the method [glossary.md](../glossary.md). Enforced by LNT-13.

## 2. Artifacts

**Workspace location — one `docs/product/` tree per product.** The vision, the vision spine, and the loop artifacts all live under `docs/product/`, so the linter resolves every citation (LNT-03) and every index (LNT-04) without crossing a directory boundary.

**Scoping — one workspace per product, not per topic.** `docs/product/` is the product's workspace: one `opportunities.md`, one `decision-log.md`, one `assumptions.md`, one `story-map.md`. Releases are the subdivision (`releases/REL<n>-*`), not topics. Every ID family is therefore globally unique per product (LNT-01) and the decision log stays the loop's shared memory. A repo holding several genuinely distinct products gives each its own `docs/product/<product>/` tree.

Domain-discovery artifacts (glossary, rules, context boundaries) are **not** duplicated here: the spine's `domain-glossary.md` plus the repo's `CONTEXT.md`/ADRs (via `domain-modeling`) are canonical, and loop skills consult and extend those.

**`SOL#` artifact.** Solution directions live in their own `solutions.md`, never as a section of `opportunities.md` — the opportunity map stays solution-neutral, and the workspace keeps one artifact per ID family. The `SOL#` model requires ≥3 materially different directions (incl. process/policy/manual-service/no-build) or an explicit `DEC#`, carries the `OPP → SOL → ASM → EXP` trace layer, and retains rejected/parked directions with reasons — linter-visible, never silently deleted. Enforced by LNT-01 (ID format/uniqueness), LNT-03 (citation integrity), and LNT-07 (the full chain including the ≥3-directions-or-`DEC#` rule).

**`DEC#` status.** A `DEC#` records uncertainty **once**, as the cited evidence's Rich/Mixed/Thin strength; it carries no confidence band. `Status` is binary — `proposed` or `confirmed`. Agents legitimately draft `DEC#` rows (LNT-07's ≥3-directions exception and LNT-18's evidence-cap override are both agent-written): an agent writes `proposed` with no owner, and the accountable owner named in `lifecycle-onepager.md`'s decision-authority record confirms it, which sets the owner field. `proposed` rows block finalize (LNT-21), so the loop's single review surface is *unconfirmed `DEC#` rows plus `OPEN:` markers*, reviewed at each skill's gate.

**Story map.** The journey backbone is a durable product-level artifact (`story-map.md`), never a per-release table and never an in-session sketch: §5.5's slice rule — *a slice must span the end-to-end journey; a single-layer slice is rejected* — is checked against a backbone that outlives the release, which makes the span rule mechanical (LNT-20). The backbone persists while each release slices it lower. No ID family — backbone steps are journey labels and cells cite existing `CAP#`/`UC#`.

**Strategy.** The vision's thin ordered-outcomes strategy section (the *Strategy (ordered outcomes)* template section of [product_vision.md](../product_vision.md)) gets **no ID family**. Strategy entries are an ordered field set — *outcome — target segment — why this order* — living in the foundation vision one-pager (elicited or stubbed by `establish-vision`) and derived and indexed under `vision-index.md`, each entry citing the vision IDs (`V#`/`S#`) it orders. Reordering the section is a routine discovery pivot (§4.2), so no durable per-entry ID exists to churn; the downstream strategy checks (§5.4, §5.5) are judgment gates reading the *current* order plus the cited vision IDs. `derive-vision-spine` reserves the strategy *field set* in its vision-index schema rather than an ID family; an index that omits a present strategy section fails the spine-completeness check (LNT-04); a stubbed section carries the canonical `OPEN:` marker (LNT-05).

### 2.2 Deterministic workspace linter

A **script, not an LLM skill** — working name `lint-workspace`; implementation language is an authoring decision — vendored with the skillset. It parses the vision spine (`<product>-vision-spine/`) and the loop workspace and reports pass/fail per check, naming the offending file and ID. It is the shared implementation of every skill's deterministic finalize checks.

**Deterministic vs. judgment.** The linter owns only what a parser can decide: presence, format, uniqueness, resolvable references, canonical markers. Everything requiring judgment — evidence quality, QAS feasibility and trade-offs, scope coherence, metric hygiene — stays in the skills' rubric/critic gates. The two result sets are always reported separately, never merged into one verdict.

**Invocation.** Every artifact-producing skill runs the applicable checks at finalize; applicable failures block finalize — except that a legitimately unresolved field carrying a canonical open marker (below) passes the check while staying visible in the report. CI or pre-commit hook integration is optional, never required.

**Canonical open-marker syntax.** A field is *explicitly open* when its value starts with the literal token `OPEN:` followed by what is needed to resolve it — e.g. `Verification: OPEN: needs a decision on the load-test rig`. This is the single spine-wide convention; every skill writes it and the linter parses it. Any other placeholder (`TBD`, `???`, an empty value) fails LNT-05, so a proposal or gap can never pass as a completed value.

**QAS field labels.** The linter parses the labels `Source:/Stimulus:/Environment:/Artifact:/Response:/Measure:` and skills emit them verbatim; *response measure* is the prose name of the `Measure:` field.

**Spine-review IDs.** `derive-vision-spine`'s local judgment rows use the `SRV#` family (*spine review*), recorded in its Phase 0 ID inventory as spine-owned so LNT-02 separates them mechanically from the loop's reserved `DEC#`.

**Routing exclusions (as material as the routes):** `north-star` is *not* attachable to `establish-vision` — metric audit is deferred past the vision stage (outcomes/signals may stay `OPEN:`; the vision handoff notes the audit occurs later) — nor to `discover-product`, which routes metric auditing to `define-release`/`validate-release`, nor to `derive-vision-spine` or `tailor-lifecycle`. Neither specialist is invocable from `derive-vision-spine`, so no specialist can acquire spine-artifact influence through derivation. `establish-vision` and `derive-vision-spine` have an empty external-dependency inventory; no skill in this plan runtime-fetches a third-party repository (§3.2 hard rule).

### 3.2 External-dependency policy

Normative for every external reuse in this skillset. Every external source resolves to exactly one of the three modes below; the mode determines the provenance record it must carry and the runtime behavior it permits. The §3.1 call-contract table is the instance of the `call` rule.

Reuse of *first-party* material — patterns carried over from other skills in this collection — is outside this policy: it needs no license, commit, or attribution record, only a note of what was carried and why it fits.

**`call` — version-pinned invocation.** A callable dependency needs all four of:

1. *Version-pinned install.* For an **external repository**: the exact commit or release, recorded in the skillset dependency manifest at authoring — never a floating branch or tag. For a **local skill**: the skill name plus its version/commit in the skills repo, recorded at authoring.
2. *Bounded contract.* Named callers, invocation condition, inputs, and outputs (the §3.1 table columns).
3. *Explicit fallback.* An unavailable callee never blocks the stage and never yields fabricated output.
4. *No ownership of spine artifacts.* A callee never owns, writes, or mutates the vision spine or the loop workspace; the calling skill records the output.

**`distill` — vendored content with full provenance.** Distilled material is vendored with the skillset — never fetched at runtime — and every vendored item carries: source repository and exact file path; commit/tag or retrieval date; license; and attribution. Donor audit and provenance capture are an **authoring-time obligation on every distilled item**: inspect the exact donor files at a pinned revision, record per-candidate dispositions and the destination skill file/section, and vendor adopted material with the four provenance fields — before any distilled text lands in a skill. The per-donor task list is §3.3. Two pinned donor snapshots cover nearly the whole distill surface: `huntsyea/product-skills` and `assimovt/productskills` (both MIT). Where two skills consume the same donor, they share one provenance record at one pinned revision; a divergence must be recorded and reconciled in both.

**`pattern` — local implementation, inspiration recorded.** The mechanism is independently authored with zero copied text; the inspiring source is recorded with repository, license, and retrieval date; there is no runtime dependency on the source. The per-skill source/dependency manifests are the realizing record of this policy.

**Hard rules.**

- **No runtime fetch.** No skill ever fetches a third-party repository at runtime (see also §3.1's routing exclusions).
- **No license-incompatible distillation.** `deanpeters/Product-Manager-Skills` (CC BY-NC-SA) is never distilled or copied — pattern/reference-only. `florianbonnet14/ThePowerOfAnalytics_ClaudeSkills` has no stated license → pattern/reference-only. Unverified or WIP licenses (`jacksoncalling/argo-continuous-discovery`, `ForceInjection/domain-driven-design-skills`) are treated as reference-only (`pattern`) until verified at audit time; distillation from any hybrid donor set is confined to its MIT members (huntsyea, phuryn) unless the unverified license is cleared.
- **Copyright-encumbered call dependencies stay call-only.** `ai-analyst-lab/north-star` embeds Amplitude-copyrighted playbook content: it is invoked per its §3.1 pin and contract but its content is never vendored.

      │

establish-vision ──► derive-vision-spine             [vision anchor + spine]
      │
      ▼
┌─────────────────────────────────────────────────────────────┐
│  THE LOOP (cadence per lifecycle.md)                        │
│                                                             │
│  discover-product                                           │
│    frame outcome → capture evidence → map OPP               │
│    → generate SOL alternatives (incl. no-build)             │
│      (≥3 materially different directions or DEC#)           │

│      │                                                      │

│      ▼                                                      │

       ↺  reopens: vision (rare) / opportunities / scope / requirements

The loop's exit criterion is the [readiness-for-design checklist](../overview.md#readiness-for-software-design): the skillset is done with a topic when those questions are answerable. What happens next (design, implementation) is outside this plan; `validate-release` re-enters from post-release evidence whenever it arrives.

Entry points other than greenfield (per [lifecycle tailoring](../lifecycle_tailoring.md)) skip forward: *new capability* enters at `discover-product`; *rework* enters at `validate-release` evidence; *compliance mandate* enters at `specify-requirements` with the mandate as a constraint; *fast-follow* enters at `define-release`.

**Discovery pivot vs. vision pivot (skillset-wide definitions).** Every adaptation the loop makes is one of exactly two kinds, and each skill's routing names which:

- A **discovery pivot** is routine discovery/validation adaptation under a stable vision: changed opportunities, solutions, scope, or strategy — including reordering the vision's thin ordered-outcomes strategy section (§2's representation decision). It is the normal case; it must never silently edit the vision. Every §4.2 route except condition 8 is a discovery pivot.
- A **vision pivot** revises the intended future itself. Only `establish-vision` and `derive-vision-spine` may make one, and only through an explicit loop `DEC#` citing evidence that invalidates the intended future or target need (§4.2 condition 8; RTS-12). A failed experiment or weak feature is refused as pivot grounds and rerouted downstream as a discovery pivot (RTS-11). `establish-vision` *cites* that loop `DEC#`; it never writes one (its no-loop-ID rule, §5.1), and `derive-vision-spine` never edits the vision at all — it routes (§5.2).

Routine findings therefore always route to opportunities, solutions, scope, or strategy first; the vision route is the rare exception, evidence-gated, `DEC#`-gated, and owned by the two vision skills alone.

### 4.1 Handover contract (skillset-wide)

Every skill in the §3 table ends a successful run with a **handover** carrying exactly these five fields. The per-skill handover bullets in §5 instantiate this contract — they name which concrete values fill each field for that skill — and none may weaken it. Regression axis 3 (§6) scores it on every run.

1. **Next applicable stage** — selected from `lifecycle-onepager.md` (entry point plus selected stages, honoring recorded skips), never from a hard-coded stage order.
2. **Changed artifacts** — the exact file paths and IDs created or modified in this run.
3. **Unresolved decisions** — the open `DEC#` entries and `OPEN:`-marked fields the next stage inherits.
4. **Progression gate** — what must be true before the next stage may run: the finalize checks passed, the applicable §2.2 linter results, and any required human confirmations.
5. **Recorded skips** — every intentionally skipped stage the handover passes over is named with the reason recorded in the one-pager; a silent skip is a blind spot and fails regression scenario RTS-02.

**Chaining guardrail.** Command chaining — one skill's handover directly invoking the next — must not override lifecycle tailoring. The mechanism is explicit: the invoked skill re-reads `lifecycle-onepager.md` at start and re-derives the applicable next stage itself; when a chained instruction contradicts the one-pager (a skipped-in stage, a bypassed gate, a roadmap demanded that the one-pager records as skipped), the one-pager wins and the conflict is resolved by the out-of-order rule below. Existing evidence hooks: RTS-02 (a chained handover must respect a recorded skip) and RTS-13 (chaining into `define-release` must not demand or drop the roadmap against the one-pager's adopt/skip record); no new scenarios are needed.

**Out-of-order execution — refuse silent violations; warn-and-record legitimate recorded deviations.** A skill invoked out of the tailored order **refuses to run** when proceeding would violate the one-pager's tailoring record or an unmet progression gate *without* a recorded reason — e.g. chaining straight to `specify-requirements` while `define-release` is neither completed nor recorded as skipped. It **warns and records** — proceeding with the deviation named in its handover and, when consequential, a `DEC#` — when the deviation is a recorded intentional skip, a re-entry per §4.2, or a reason the human states and the skill records on the spot. Recording converts a silent violation into a legitimate one, so refusal is always escapable, never silently: the one-pager guides, recorded human judgment overrides, silence never does.

### 4.2 Re-entry definition (skillset-wide)

Re-entry — reopening an earlier artifact and resuming the loop there, per the §4 diagram — is always a **route**, never a generic "revisit earlier work". Every route carries six fields (enforced for reviews by LNT-17): the exact reopened artifact IDs, one named accountable owner, the preserved (non-reopened) decisions, the required new evidence, urgency, and a closure condition. Perseverance — reopening nothing — is recorded with its rationale just as reopening is. A route in flight is a legitimate deviation under §4.1's out-of-order rule (warn-and-record, not refuse).

The `validate-release` backtracking conditions map to routes as follows (§5.7 instantiates this table and adds the verdict/urgency fields at review time):

| # | Post-release finding | Artifact reopened | Skill re-entered |
| --- | --- | --- | --- |
| 1 | Capability used, outcome unmoved | Opportunity selection / `REL` scope (`OPP#`, `CAP#`) | `define-release` |
| 2 | Capability barely used | Value assumption (`ASM#`/`OPP#`) | `discover-product` |
| 3 | Misuse or workarounds | Journey/usability assumption (`UC#`) | `discover-product` and/or `specify-requirements` |
| 4 | Guardrail breached | Lowest challenged artifact: `REL` scope, `REQ#`, `QAS#` — a vision principle only via condition 8 | `define-release` / `specify-requirements` |
| 5 | Incident, support burden, poor recovery, degraded mode | `QAS#` and related `REQ#` | `specify-requirements` |
| 6 | Audit/compliance finding | Obligation, trace, requirement, transition behavior | `specify-requirements`; `define-release` when a scope commitment changes |
| 7 | Terminology/rule/ownership confusion | Canonical domain artifacts (`domain-glossary.md`, `CONTEXT.md`/ADRs) | `domain-modeling` — **not one of the seven skillset skills**: an external/local call per the §3.1 contract; affected requirements then follow via `specify-requirements` |
| 8 | Foundational actor/outcome/value/boundary assumption contradicted | The vision — only through an explicit `DEC#` citing the invalidating evidence (RTS-12) | `establish-vision`, then a `derive-vision-spine` refresh; the evidence chain is preserved |
| 9 | Evidence too weak or instrumentation invalid | Analysis plan and observation requirement | None — no scope verdict; measurement repair stays inside `validate-release` |
| 10 | Scope retired | Transition requirements (LNT-12) | `specify-requirements` |

**Tailoring re-entry.** The one-pager's revisit triggers (§5.3) feed this same definition: each trigger is a concrete evidence condition naming the tailoring decision reconsidered, and when it fires the route's reopened artifact is `lifecycle-onepager.md` itself, its skill `tailor-lifecycle`, and its closure condition a re-tailored one-pager that downstream skills then follow.

**In-loop backtracking** uses the same route schema: `discover-product`'s *adapt* reopen, `define-release`'s backtracking-trigger matrix, `specify-requirements`' failed-gate routes, and the vision-stage route tables each resolve to a named artifact, owner, and closure condition — regression axis 4 (§6) scores re-entry landing on the reopened artifact with resolvable IDs.

## 5. Per-skill sections

### 5.1 `establish-vision`

- **Mode:** interview — divergent exploration of the intended future, converging on one anchor.
- **Does:** elicits the [product_vision.md](../product_vision.md) template's sections — actors, desired change, value, principles, boundaries, success signals — plus the thin Strategy section below. Writes `<slug>-foundation-vision.md` and `<slug>-foundation-vision-architecture-lens.md` under `docs/product/`; configured overrides are honored. Writes `S/V/UC/BV` IDs only — it *cites* loop IDs, never writes one.
- **Emit visible gaps at finalize.** The finalized vision ends with stub sections for what the interview deliberately does not elicit — *product principles*, *outcomes and signals*, *critical assumptions* — so the [product_vision.md](../product_vision.md) completion checks fail loudly, not silently. `discover-product` picks the assumptions stub up as its seed.
- **Finalize gate:** the six completion checks from [product_vision.md](../product_vision.md); uncovered sections are open stubs, never silently passed.
- **Tailoring pointer.** One line at session start: for non-greenfield topics, suggest `tailor-lifecycle` first — an existing vision may need extending, not a new session.
- **Principles micro-phase — this skill owns the product-principles stub.** A short convergent add-on after the ladder closes: harvest the session's recurring trade-offs ("we kept choosing X over Y, and here is why") into 3–5 product principles, populating the *product principles* stub. Those trade-offs are live in the session's context there and nowhere later. Optional and ceremony-gated: when skipped, or under a low-ceremony one-pager, the stub keeps its canonical `OPEN:` marker (LNT-05) and stays a visible gap that a later session — including `discover-product` via a recommendation to the vision's accountable owner — can close. The skill never invents principles the session did not actually exhibit.
- **Optional press-release stress test.** A convergent stress test after divergence, before final acceptance: explain the intended future, beneficiary, and value in press-release language; a feature-shaped vision fails and the exposed gap routes back to the specific failing vision section. Pattern-only — independently authored, zero Dean Peters wording (CC BY-NC-SA).
- **File-responsibility contract.** Orchestration in `SKILL.md`, interview behavior in phase sub-files, reusable checks/templates in focused reference files — every rule lands in its owning sub-file.
- **Handover UX.** The finish response instantiates the §4.1 handover contract: the next applicable stage per `lifecycle-onepager.md` — `derive-vision-spine` for greenfield, back to the tailored lifecycle otherwise — the changed artifacts (the foundation-vision path and its `.wip.md` state), the unresolved decisions (the deliberate `OPEN:` stub sections the loop inherits, including the deferred metric audit), the progression gate (the method doc's finalize checks plus the linter set below), and any recorded skip the handover passes over; never a generic "what next?".
- **Low-ceremony guarantee.** Only bounded finalize checks; configured use-case limits and lifecycle tailoring are honored; a low-ceremony topic completes with the minimum artifact plus explicit `OPEN:` stubs.
- **Human gate on scope; decision ownership.** The agent can never climb or close the scope ladder itself; a scope-significant architecture-sweep finding follows the documented route back through the scope lens. The vision **finalize/reopen decision** carries the ownership depth of §5.3's seven-field record: one named accountable owner per `lifecycle-onepager.md` — for a greenfield topic without a one-pager yet, the human names the owner in-session and the finalize output records it — and a group or department offered as owner is refused (RTS-07). The skill fabricates no specialist evidence: the architecture-significance sweep parks genuine technical constraints for the responsible specialists instead of inventing engineering/security/compliance answers (RTS-08), and the finalize output records the accountable owner plus the specialists consulted or their explicit absence.
- **Durable-state rule.** All resume state lives in the repo-resident `.wip.md` and the finalized foundation vision — never only in chat. The resume scan reads `docs/product/` for prior `*.wip.md` and finalized `*-foundation-vision.md` work.
- **Strategy section.** The skill elicits — or explicitly stubs with an `OPEN:` marker — the vision one-pager's thin **Strategy (ordered outcomes)** section per the [product_vision.md](../product_vision.md) template (*outcome — target segment — why this order*). It joins the section coverage and the finalize gate like every other recommended section — populated or explicitly open, never silently absent. The skill never expands it into a roadmap (roadmap adoption is a `tailor-lifecycle` ceremony decision, §5.3/LNT-14), and later reordering of the section is a §4 discovery pivot, not a reason to reopen this skill. No ID family (§2); entries cite the `V#`/`S#` they order. `derive-vision-spine` derives and indexes the section (§5.2).
- **Backtracking route table; vision-pivot gate.** Every trigger has a named destination, no informal "reopen if needed": completion-check failure → the relevant finalize section; scope-significant sweep finding → the scope lens; a reopened, changed vision → the affected finalize checks plus a `derive-vision-spine` rerun. The route table additionally carries the §4 vision-pivot trigger: **reopening a finalized vision requires an explicit loop `DEC#` citing evidence that invalidates the intended future or target need** — the skill *cites* that `DEC#` from the loop workspace (its no-loop-ID rule stands: it writes only `S/V/UC/BV`, never a `DEC#`), and a failed experiment or weak feature offered as pivot grounds is refused and rerouted downstream as a discovery pivot (opportunities, solutions, scope, or strategy). RTS-11 scores the refusal; RTS-12 scores the genuine pivot with the `DEC#` recorded and the finalize checks rerun.
- **Provenance and dependency discipline.** The skill's external-dependency inventory is empty — no runtime fetch, no unpinned external call (see §3.1's routing exclusions: no `north-star` at vision stage). The §2.1 method-doc coverage row is a normative authoring input with a drift trigger on any consumed-doc change (§3.3).
- **Finalize runs the deterministic linter (§2.2):** LNT-01 (`S/V/UC/BV` format and uniqueness), LNT-05 (the deliberate stub sections carry canonical `OPEN:` markers, so they fail loudly and parseably), LNT-13.

### 5.2 `derive-vision-spine`

- **Mode:** AFK derive — an orchestrator with builder/critic sub-agents, a durable judgment log, and a human gate at the end.
- **Does:** derives `<product>-vision-spine/` from the frozen foundation vision under `docs/product/` (configured overrides honored): actors, `domain-glossary.md`, invariants, capability map, `uc-index.md`, `vision-index.md`, and `discovery-seeds.md`. Assigns `INV`/`CAP` IDs and its own `SRV#` judgment rows. **Derived-only: no loop artifacts inside the spine**, and the skill never edits the vision.
- **Discovery seeds.** `discovery-seeds.md` lists the derivation's discovery-relevant signals — unpromised UCs, coverage gaps in `vision-index.md`, low-confidence judgment rows — explicitly as candidate `OPP`/`ASM` inputs, README-linked and included in the spine-completeness checks, so `discover-product` starts from the seeds instead of re-reading the whole spine. Seeds cite IDs and questions only: the hypothesis/experiment schema (`EXP#`, method, time budget, criteria) belongs to `discover-product` and is forbidden in seed content.
- **Reserve the loop's ID families** (`ASM`, `EV`, `OPP`, `SOL`, `EXP`, `REL`, `REQ`, `QAS`, `DEC`) in the Phase 0 ID inventory so no collision arises later; `solutions.md` is excluded from derivation — the spine never contains solution content.
- **The ubiquitous-language file is `domain-glossary.md`** (design principle 7): the *product's* language, distinct from the method terms in [glossary.md](../glossary.md).
- **Mechanical gates run as the shared linter (§2.2) at finalize:** source-ID coverage, derived-ID uniqueness, resolvable references, and reserved-namespace absence map to LNT-01–LNT-05 plus LNT-13; the spine's local judgment rows use the `SRV#` family so they stay mechanically distinguishable from the loop's reserved `DEC#` (LNT-02).
- **Builder/critic independence gate.** Builders and critics run in separate fresh contexts; a critic brief contains the frozen vision, the draft artifact, the template, and the rubric — never builder reasoning or expected verdicts. Independent multi-critic reviews use spine-specific rubrics (no imported NFR content).
- **Backtracking/re-entry matrix.** Every mechanical and critic finding category routes to the phase that owns the defective artifact; cross-phase defects reopen the minimal closure and rerun global gates; no route may end in an unspecified "review later".
- **Durable status and human gate; vision-pivot gate.** `_status.md` and review files stay durable; the final human gate adjudicates residual judgment; coverage gaps become routed seeds or judgment rows — the skill never silently "repairs" the vision. The **vision-drift → user-confirmed full rebuild** route requires an explicit loop `DEC#` — recorded in the loop workspace, since `DEC` stays reserved in the spine (LNT-02) — citing the evidence that invalidates the intended future or target need, *before* the rebuild is offered for user confirmation; a rebuild attempt without that cited `DEC#` is refused and the finding becomes a routed seed or judgment row instead (RTS-11/RTS-12 hooks). All other findings are discovery pivots routed to seeds or judgment rows, never vision edits.
- **Strategy derivation and reserved fields.** The skill **derives and indexes** the vision's Strategy (ordered outcomes) section under `vision-index.md` — round-tripping the ordered entries without reordering or rewriting them, each entry citing its `V#`/`S#` — and reserves the strategy *field set* (ordered outcome, target segment, ordering rationale) in its schema per §2 (no ID family). A missing or `OPEN:`-stubbed strategy section is a visible coverage finding and discovery seed, never silently repaired; an index that omits a present strategy section fails the spine-completeness check (LNT-04). The derived index is what the §5.4/§5.5 opportunity-selection-vs-strategy checks read; strategy reordering is a discovery pivot executed upstream in the vision file, never a spine edit.
- **Handoff gate.** The finalize response instantiates the §4.1 handover contract: the next lifecycle skill per `lifecycle-onepager.md`, the changed artifacts (the spine path and `discovery-seeds.md`), the unresolved decisions (the open `SRV#` judgment rows and coverage gaps awaiting the human gate), the progression gate (spine-completeness checks plus that human gate), and any recorded skip passed over. Command chaining must not override lifecycle tailoring: a chained next step that contradicts the one-pager resolves per §4.1's chaining guardrail and out-of-order rule.
- **Schema and dependency guardrails.** Progressive disclosure throughout — every rule lands in its owning sub-file per the file-responsibility map; the schema inventory contains only proprietary artifacts/IDs (no PRD, `CP/CN/FR`, or third-party workspace structures); the dependency inventory has no runtime third-party calls, and pattern sources are recorded with repository, license, and retrieval date. Neither `north-star` nor `quality-attribute-scenario-writer` is invocable from this skill (§3.1).

### 5.3 `tailor-lifecycle` (new)

- **Mode:** short interview — adaptive depth: a compact component-selecting workflow that asks only enough to resolve entry point, ceremony, cadence, artifacts, authority, and revisit trigger, staying within a 10–15-question target for low-risk topics and deepening only on risk or ambiguity, with the reason recorded. Output is one file.
- **Does:** classify the topic (greenfield / new capability / rework / mandate / fast-follow / platform), size ceremony per driver, select which loop skills and artifacts this topic uses, set cadence and decision owners. Writes `lifecycle-onepager.md` — the sole output; canonical method terminology throughout; no donor workspace, taxonomy, or stage-artifact scheme.
- **Key behavior:** the minimum-ceremony package is the default path for low-risk solo work — full ceremony is never the default; stages and artifacts are recommended only when they reduce an important uncertainty or improve a consequential decision (completeness-driven selection is a guarded failure mode); every known stage not selected is explicitly recorded as skipped with a reason ("a silent skip is a blind spot"), and finalize fails when a stage is neither selected nor explicitly skipped. Other loop skills read `lifecycle-onepager.md` at start and respect it.
- **Roadmap ceremony gate:** the one-pager records **adopt** or **skip** for the optional roadmap, with the deciding driver — coordination cost, sponsor communication, or product lifetime. Adoption hands the maintenance obligation to `define-release`; skip means the strategy list and decision log are sufficient and no downstream skill may demand a roadmap. LNT-14 is armed only for adoption, and RTS-13 exercises both variants.
- **Handover:** every successful run ends by naming the selected entry skill, the later enabled stages, the reason, and the required input artifact — the next stage is derived from entry point plus selected stages, not a hard-coded order (rework → validation evidence, mandate → requirements, fast-follow → definition). This is the producing end of the §4.1 handover contract: the one-pager this skill writes is the record from which every later handover derives its next-applicable-stage field, the record the §4.1 chaining guardrail defends against command chaining, and the record whose silent violation the §4.1 out-of-order rule refuses — while recorded skips and §4.2 re-entries proceed as warn-and-record.
- **Revisit trigger:** the one-pager's revisit trigger is a set of concrete evidence conditions, each naming which tailoring decision is reconsidered — never "revisit when needed". Each trigger is a §4.2 re-entry route into `tailor-lifecycle` itself: the reopened artifact is `lifecycle-onepager.md`, and the closure condition is a re-tailored one-pager that downstream skills then follow.
- **Ownership gate — the seven-field decision-authority record:** the one-pager's decision-authority section records, for every consequential decision type and selected stage, all seven ownership fields from [collaboration_and_decision_ownership.md](../collaboration_and_decision_ownership.md): (1) exactly **one named accountable owner** — a group, trio, or department is never an accountable owner and is rejected at finalize (RTS-07); (2) **required contributors**; (3) **specialist authorities**; (4) **formal approvers**, where a contractual, regulatory, funding, or governance process requires them (approval never replaces the accountable owner); (5) the **evidence required to decide**; (6) the **escalation path**; (7) the **evidence-based reopen trigger** — which feeds the revisit triggers. A legitimately unresolved field carries a canonical `OPEN:` marker (LNT-05); finalize blocks on a missing field or a group-only owner. The tailoring interview includes a **specialist-participation question**: which specialist evidence — engineering, design, operations, security, compliance, domain, or other — is material for this topic; the answers become the named required contributors and specialist authorities that downstream skills gate on (RTS-08). Role names from the method doc's default ownership matrix are replaced with actual people; in a small team one person may hold several roles, but the roles are recorded separately so missing perspectives stay visible. Design and architecture decisions stay under engineering/architecture authority — the future design skillset's territory (§7) — never product-management authority by default. This one-pager record is the single source every downstream ownership gate reads (`DEC#` owners in §5.4, `REL` decision metadata in §5.5, requirements human-gate owners in §5.6, review/re-entry owners in §5.7); a handover crossing a decision-authority boundary without the named owner and escalation path from this record is refused (RTS-09). These rules live in the seven skills and the one-pager itself — no standalone ownership skill and no additional mandatory runtime document.
- **Provenance:** runtime calls pinned, distilled material carries full provenance, no donor repo is ever fetched at runtime — the external-dependency policy (§3.2) is the normative statement of these rules; the six-repo pattern audit is an authoring-time task (§3.3).
- **Finalize:** runs the deterministic linter (§2.2) — LNT-05 and LNT-13 on the one-pager — reported strictly separately from the judgment review; applicable failures block except under the open-marker policy; its roadmap adopt/skip record arms LNT-14 for `define-release` only when the roadmap is adopted. The judgment rubric runs all **eight** completion checks from [lifecycle_tailoring.md](../lifecycle_tailoring.md): (1) entry point matches uncertainty; (2) skips are recorded with reasons; (3) roadmap adoption or skip is explicit and justified by coordination cost, sponsor communication, or product lifetime; (4) ceremony matches risk, irreversibility, and regulation per driver; (5) one cycle has a defined decision output; (6) every consequential decision type has one named owner and an escalation path; (7) contributors, specialist authorities, and approvers are named where applicable; and (8) a revisit trigger exists. RTS-13 exercises both roadmap variants, and the adopted variant arms LNT-14; this is the existing roadmap gate, not an additional completion check.
- **Regression hooks:** scenarios RTS-01 (low ceremony), RTS-02 (recorded skip), and RTS-13 (roadmap adopt/skip) of the reference-topic rubric (§6) exercise this skill's gates; the skill runs inside the scored end-to-end reference-topic run.

### 5.4 `discover-product` (new)

- **Mode:** interview for evidence and judgment; light derive for restructuring maps.
- **Granularity — one skill, not two.** `discover-product` is a single skill with one wrap-up gate: `SKILL.md` orchestrates, one progressive-disclosure sub-file per discovery step. The seven steps are one continuous evidence-building session; splitting mid-loop would push the workspace state through a skill boundary and duplicate the wrap-up gate.
- **Context strategy — progressive disclosure plus sub-agents.** Being one skill must not mean one bloated context. Two mechanisms, applied per phase. *Progressive disclosure:* only `SKILL.md` loads at invoke; a phase sub-file enters context when its phase runs. *Sub-agents* absorb the derive-heavy phases, so the bulky distilled method material and vendored source trails (design principle 6) are read by sub-agents and never by the orchestrator. The seam is who must talk to the human — a sub-agent cannot interview:

  | Step | Runs in | Why |
  | --- | --- | --- |
  | Frame outcome | main session | human judgment |
  | Capture evidence (`EV#`) | main session | only the human has it; the skill coaches, never fabricates |
  | Map opportunities (`OPP#`) | main session | add/merge/escalate/park routing is the human's |
  | Generate alternatives (`SOL#`) | sub-agent drafts → human selects | generation is derive work; material difference is the §5.4 judgment gate |
  | Map assumptions (`ASM#`) | sub-agent drafts from `SOL#` → human ranks | derivable from solutions; importance × evidence is judgment |
  | Experiment cards (`EXP#`) | sub-agent drafts the eleven fields → human predeclares criteria | LNT-19 forbids post-hoc criteria, so criteria and budget stay with the human |
  | Wrap-up gate | sub-agent critic + linter script | mechanical checking |

  Every sub-agent follows the independence rule: it receives artifacts, schemas, and rubrics — never builder reasoning or an expected verdict — and its drafts return marked *awaiting review*, never silently adopted.
- **Does:** the [discovery loop](../product_discovery.md#discovery-loop) — frame the outcome; coach the human through evidence capture (`EV#` — the agent asks about *specific past behavior*, never accepts hypothetical enthusiasm as strong evidence); map opportunities (`OPP#`) separately from solutions; **generate alternatives** (`SOL#`) — ≥3 materially different solution directions for the targeted opportunity, including process, policy, manual-service, and no-build options where plausible, or an explicit `DEC#` recording why alternatives are not viable, recorded in `solutions.md` with rejected/parked directions retained and reasoned; expose and rank assumptions (`ASM#`) by the four risks, each citing the `SOL#` it belongs to (or `OPP#` only when solution-independent); draft experiment cards (`EXP#`) per the merged schema below — explicit assumption/hypothesis content plus predeclared support/refute/inconclusive criteria, each card citing its target `ASM#` and the applicable `SOL#`; record the proceed/adapt/pause/abandon decision (`DEC#`).
- **Distilled technique base.** The skill's reference sub-files vendor distilled techniques and anti-patterns — the seven-step loop's techniques and phase anti-patterns (huntsyea `continuous-discovery`), the optional JTBD switch-interview/forces lens routed only for motivation/switching uncertainty, and the cheapest-trustworthy-test method selection across all four risks (prototype, concierge/Wizard-of-Oz, spike, data analysis, demand test, policy/security/legal review, pilot). Every relevant anti-pattern maps to a guardrail, finalize check, or explicit rejection in an anti-pattern coverage table. All distills are audit-conditioned on the §3.3 donor audit (repo, path, pinned revision, retrieval date, license, attribution). Premature-convergence coaching is authored independently — reference-only, no Dean Peters text.
- **Evidence quality.** Interview guardrails ask for concrete recent behavior (Mom-Test style) and classify opinions/hypotheticals as weak; the problem-validation rubric (frequency / intensity / willingness-to-pay or a justified substitute) is applied without treating it as universal; every interview-derived `EV#` is classified Rich/Mixed/Thin, and confidence is capped by evidence quality — three Thin items never mechanically become Rich; exceeding the ceiling requires an explicit `DEC#` (LNT-18).
- **Opportunity routing and the human gate.** Every evidence-derived opportunity gets a routing decision — add / merge / escalate / park — with provenance preserved on merge and reasons on park/escalate; a human gate precedes solution generation: evidence is never silently converted into solutions, and AFK-produced proposals are marked *awaiting review*.
- **Integrations:** seeds from the spine's `discovery-seeds.md` and the vision's critical-assumptions stub; "test cheaply" may hand off to `prototype`, and contested domain language triggers `domain-modeling` — both per the §3.1 call contracts with explicit fallbacks; pause/resume via durable repo-resident `.wip` state; all `EV/OPP/SOL/ASM/EXP/DEC` records stay discoverable via the workspace index (LNT-04); a separated critic may review derived maps/cards — it gets artifacts and rules, never builder expectations.
- **Guardrail:** the skill *coaches* evidence-gathering, it never fabricates evidence. An `EV` row without a human-supplied source is invalid; missing evidence stays an explicit gap.
- **Guardrail — alternative-count refusal:** the skill refuses to *rank* solution assumptions while fewer than three materially different solution directions are on the table, unless a `DEC#` records why alternatives are not viable — the refusal fires at ranking time, not only at finalize. The wrap-up gate additionally re-runs the method doc's completion check *alternative solutions were considered*. Regression scenario RTS-04 (§6) exercises the single-solution case below this threshold — ranking refused without the `DEC#`, permitted with it — and scores the completion check.
- **Guardrails — discipline:** architecture-changing quality risks surface early as *classified assumptions*, explicitly not `QAS#`; no donor IDs, folders, or taxonomies enter the workspace — one proprietary spine; decision thresholds are predeclared so research ends (endless research cannot complete without thresholds or an explicit open decision).
- **Experiment-card schema.** Every `EXP#` card is the [method doc's complete experiment-card template](../product_discovery.md#experiment-card) merged with the spine — eleven fields: **decision to inform** (what decision this evidence informs), **assumption/hypothesis** (the explicit content under the method card's `## Assumption`, not merely an `ASM#` citation), **target `ASM#`**, **applicable `SOL#`**, **evidence needed** (what must be observed), **method** (the cheapest trustworthy test), **time budget** (research ends — pairs with the thresholds above), **predeclared support/refute/inconclusive criteria** (written before the test runs, never post-hoc), **result**, **confidence per relevant risk dimension** (value/usability/feasibility/viability — only the dimensions the target `ASM#` is classified under), and **resulting `DEC#`** (the proceed/adapt/pause/abandon entry the result fed). The first eight are required-resolved when the card is finalized; a missing or `OPEN:` assumption/hypothesis fails LNT-19. Result, per-risk confidence, and resulting `DEC#` may carry `OPEN:` markers until the experiment has run (LNT-19; citation integrity via LNT-03/LNT-07). The `prototype` call contract (§3.1) passes and returns exactly these fields.
- **Wrap-up and backtracking:** the wrap-up names the proceed/adapt/pause/abandon verdict, the next lifecycle stage from the one-pager, and the exact input artifacts; an *adapt* verdict becomes an explicit reopen instruction naming the affected `SOL#`/`ASM#`, never an indiscriminate restart. The wrap-up instantiates the §4.1 handover contract — the next applicable stage per the one-pager, the changed artifacts (the discovery files and `EV/OPP/SOL/ASM/EXP/DEC` IDs touched), the unresolved decisions (open `ASM#`/`EXP#` items and `OPEN:`-marked card fields), the progression gate (the wrap-up completion checks plus the linter set below), and any recorded skip passed over — and an *adapt* reopen is a §4.2 route: exact IDs, one named owner, preserved decisions, required new evidence, and a closure condition.
- **Discovery-pivot vs. vision-pivot routing:** every adapt decision is a §4 **discovery pivot** within the stable vision — `discover-product` never edits the vision. When evidence appears to invalidate the intended future or target need, the wrap-up routes a **vision re-entry recommendation** to `establish-vision` via an explicit `DEC#` citing that evidence (the §4 vision-pivot gate); a failed `EXP#` or weak feature proposed as vision-rewrite grounds is refused at wrap-up and rerouted to opportunities, solutions, scope, or strategy (RTS-11; the genuine case is RTS-12).
- **Opportunity selection vs. strategy:** opportunity selection (the routing/targeting decisions above) is checked against the vision's thin ordered-outcomes strategy section, read from the spine's derived strategy index; selecting against the recorded order needs an explicit `DEC#` — never a silent divergence and never a silent reorder. Reordering the strategy itself is a §4 discovery pivot: recorded as a `DEC#` and applied to the vision one-pager's strategy section by its accountable human owner (no vision pivot, no `establish-vision` reopen — the skill recommends, the human edits), after which the spine's derived strategy index is refreshed; it is never a spine edit.
- **Decision ownership and specialist participation:** the owner field of every proceed/adapt/pause/abandon `DEC#` names the one accountable individual recorded in `lifecycle-onepager.md`'s decision-authority section (§5.3) — a group, trio, or department as owner is refused (RTS-07). A `DEC#` the skill or a sub-agent drafts — including LNT-07's ≥3-directions exception and LNT-18's evidence-cap override — is written `Status: proposed` with no owner, and is confirmed only by that accountable individual, which sets the owner field (§2's status decision); `proposed` rows block the wrap-up gate (LNT-21). When a decision's feasibility, viability, or quality evidence is material, actual specialist input — engineering, design, operations, security, compliance, domain — is required per the one-pager's named specialist authorities; the skill never fabricates specialist evidence (extending the classified-assumption discipline and evidence non-fabrication above): the missing input stays an explicit `OPEN:` gap and the decision is refused until the input is supplied or the accountable owner records the gap in the `DEC#` (RTS-08).
- **Finalize runs the deterministic linter (§2.2):** LNT-01, LNT-03–LNT-07, LNT-18, LNT-19, LNT-21 on the discovery artifacts — including the `EV#` human-supplied source/date/strength rule (LNT-06), the full `SOL` chain (LNT-07), the evidence-confidence cap (LNT-18), and all eleven experiment-card fields per the merged schema, with a missing or unresolved assumption/hypothesis rejected (LNT-19); the wrap-up gate's judgment checks stay separate. A blind reference-topic run scores the skill against its completion checks (§6).

### 5.5 `define-release` (new)

- **Mode:** interview — selection and prioritization are human judgment; the agent enforces the discipline.
- **Does:** [product definition](../product_definition.md)'s activities — select `OPP`s (record deferrals with reasons); express scope as capabilities in solution-neutral language (reusing/extending the spine's `CAP` map); check the boundary against the vision's `S`-ladder and escalate to a vision conversation when scope fights it; prioritize with the stated criteria (every "must" needs a consequence; ties break by learning value); cut a thin coherent slice and name the hypothesis it tests, with success/guardrail/stop criteria. Writes `releases/REL<n>-definition.md`.
- **Journey shaping and slice discipline — `story-map.md` is a durable artifact.** `define-release` writes the product's journey backbone to `story-map.md` on the first release that needs it and extends it thereafter; each `REL<n>-definition.md` records the slice it cuts — which backbone steps it touches and which it explicitly defers (§2's story-map representation decision). A progressive-disclosure story-mapping reference (distilled from the MIT huntsyea donor; its donor audit is an authoring-time task, §3.3) supports shaping the backbone and cutting the slice. The span rule is now mechanical: a slice must span the end-to-end journey — a single-layer slice is rejected — enforced by LNT-20 against the durable backbone rather than against a table the release wrote itself. Ceremony-gated: a one-pager recording a deliberate story-mapping skip produces no map and disarms LNT-20. The *coherent* half stays judgment — scope-cutting prompts and a finalize failure check distinguish *small* from *coherent*, and a slice of disconnected items fails finalization even when it satisfies LNT-20's span check. The backbone is never invented to fit a slice: extending it is a shaping decision recorded like any other.
- **Proportional ceremony.** An optional shaping/appetite path is ceremony-gated: appetite and commitment discipline are recorded *inside* the `REL` artifact, never a separate pitch artifact; a proportional-investment (bet-sizing) check ties investment to uncertainty, reversibility, and learning value, complementing the release stop criteria — a reversible uncertainty gets a smaller bet than an irreversible regulated commitment.
- **Mandatory-scope classification.** Every mandatory scope driver is classified Obligation / Expectation / Hope, and each obligation records the consequence that makes it mandatory — no `CP/CN/FR` identifiers; enforced deterministically by LNT-15 and consumed downstream by `specify-requirements` (LNT-16).
- **Hypothesis quality.** The `REL` hypothesis section predeclares how the release will be judged after shipping — success/failure/inconclusive interpretation, confidence per risk dimension, time budget, and investment boundary — so the release is judgeable without post-hoc criteria invention. This mirrors the merged `EXP#` schema's predeclared-criteria discipline (§5.4): a release is a bigger experiment, and its interpretation criteria, per-risk confidence, and time budget are written before shipping just as an experiment card's support/refute/inconclusive criteria and budget are written before the test runs; `validate-release` later holds the review to exactly these precommitted criteria (LNT-08, LNT-17).
- **Metric audit.** When outcome-metric hygiene is material, the release's success measures go through the version-pinned `north-star` callable specialist per the §3.1 contract (audit result or justified skip recorded in `REL` review metadata; local-review fallback); locally authored metric-tree prompts (MIT phuryn material, adapted) prepare candidate outcome/driver/input decompositions for that audit — never a second runtime dependency.
- **Guardrails:** refuses a release without a hypothesis or stop criteria; refuses scope items that trace to no `OPP`/evidence without an explicit `DEC` override — every scope decision resolves to evidence or carries the override.
- **Handover and backtracking:** the final response names the next stage selected by `lifecycle-onepager.md`, all required input files, unresolved blockers, and the resume point — `specify-requirements` must be able to start without rediscovering state; a backtracking-trigger matrix (pattern-only local implementation — the ForceInjection donor license is WIP/unverified, so nothing is copied) maps each trigger to one artifact, decision owner, and next skill: back to discovery, a vision re-entry request, domain work, or stopping definition; an ambiguous "go back" fails review. The final response instantiates the §4.1 handover contract — the next stage per the one-pager, the changed artifacts (`REL<n>-definition.md` and the `REL#`/`CAP#` records), the unresolved decisions (the named blockers and open `DEC#` items `specify-requirements` inherits), the progression gate (the guardrails above plus the linter set below), and any recorded skip passed over. The trigger matrix's rows are §4.2 routes (one artifact, one owner, next skill, closure condition), and the post-release conditions that reopen a release land here through the §4.2 condition map (conditions 1, 4, and 6 route to `define-release`). The matrix's vision trigger is sharpened by the §4 pivot definitions: **a vision-boundary conflict routes to a vision re-entry request — an explicit `DEC#`-carrying route to `establish-vision` — never a vision edit or a silent scope expansion**; `define-release` makes discovery pivots only (back to discovery, scope, or strategy), and a failed release or weak feature offered as vision-rewrite grounds is refused and rerouted (RTS-11; the genuine `DEC#`-gated case is RTS-12).
- **Opportunity selection vs. strategy:** the selection step checks the chosen `OPP`s against the vision's thin ordered-outcomes strategy section, read from the spine's derived strategy index: a selection that fights the recorded order needs a strategy conversation and an explicit `DEC#` — a recorded discovery pivot reordering the strategy section, or a recorded exception — never a silent reorder, a silent divergence, or a vision edit.
- **Ceremony-gated roadmap maintenance:** only when `lifecycle-onepager.md` records roadmap adoption (the `tailor-lifecycle` decision, driven by coordination cost, sponsor communication, and product lifetime — §5.3, arming LNT-14) does `define-release` maintain the **outcome-based rolling now/next/later view**: each entry names an outcome (feature-only or date-only entries fail LNT-14), *now* mirrors the committed `REL` slice, *next/later* mirror the strategy section's remaining ordered outcomes, and the view is revised as evidence arrives — never committed features-and-dates. A skipped-roadmap topic produces no roadmap and nothing downstream may demand one (RTS-13 scores both variants).
- **Decision-metadata ownership and specialist participation:** the `REL`'s decision metadata (the owner/date/review fields LNT-15 checks) carries §5.3's full seven-field depth for the release commitment, per `lifecycle-onepager.md`: one named accountable owner — a group or department as owner fails finalize (RTS-07) — plus required contributors, specialist authorities, formal approvers where applicable, the evidence required to decide, the escalation path, and the evidence-based reopen trigger. When usability, feasibility, viability, or quality evidence is material to scope, the named design/engineering/operations/security/compliance/domain input is present before the release finalizes — a missing required specialist input blocks finalize or is recorded as an explicit `DEC#` skip with the gap carrying an `OPEN:` marker (RTS-08); the skill fabricates no specialist evidence.
- **Finalize runs the deterministic linter (§2.2):** LNT-01, LNT-03–LNT-05, LNT-08 (hypothesis + success/guardrail/stop criteria), LNT-09 (an instrumentation/observation requirement per outcome and guardrail criterion), LNT-15 (O/E/H classification, capability→opportunity/evidence resolution, deferral reasons, decision owner/date/review fields), LNT-21 (no `proposed` `DEC#` survives finalize), and — armed conditionally — LNT-14 when the one-pager records roadmap adoption, LNT-20 when `story-map.md` exists.

### 5.6 `specify-requirements` (new)

- **Mode:** AFK derive with a human review gate — an orchestrator with builder/critic sub-agents and a durable judgment log, at smaller scale than `derive-vision-spine`. Most content is restructuring the committed slice; conflicts and gaps go to the human.
- **AFK boundary — full AFK elaboration, grouped marked-proposal review.** Use-case elaboration invents failure paths, which is judgment, but that does **not** make the skill stop per use case. The builder elaborates every `UC#` unattended; any failure path, target value, term, or rule not traceable to a `UC#`/`INV#`/`EV#`/`REL` source is auto-marked a proposal with the canonical `OPEN:` marker, which blocks finalize (LNT-05). The review gate then walks **only the marked proposals** — clean UCs never interrupt the human — **grouped by pattern**, so a gap repeated across many use cases resolves as one ruling applied to all of them (twelve "no timeout path specified" → one decision, not twelve). The queue therefore grows with *distinct* judgment gaps, not with use cases. A slice large enough that grouped proposals still overwhelm review is a signal that `define-release` cut too big a slice — the fix is the slice boundary below, never a cheaper review. The critic may pre-triage low-stakes proposals so contested ones surface first; it never resolves one.
- **Does:** for one `REL`: elaborate the in-scope `UC`s with alternative and failure paths ([use cases doc](../use_cases_and_story_mapping.md)); specify functional/interface/data/transition requirements (`REQ#`) in the trigger–response–constraint form from [requirements_engineering.md](../requirements_engineering.md); sharpen quality attributes into measurable scenarios (`QAS#`), seeding from the `*-architecture-lens.md`; maintain traceability `EV/OPP → SOL → CAP → UC/REQ/QAS` (the discovery-side chain `OPP → SOL → ASM → EXP` is owned by `discover-product`, §5.4).
- **Fresh-critic protocol.** The requirements critic runs in a separate context receiving the authoritative input artifacts, candidate outputs, schemas, gates, and lint results — never builder reasoning or expected verdicts; seeded plausible errors must be detected, and the verdict stays stable when builder rationale is withheld.
- **Durable-workspace discipline.** Rejected and unresolved alternatives are preserved as durable artifacts; indexes and handover lists must match the files actually present (LNT-04) — stale indexes and missing rejected alternatives fail validation.
- **Slice boundary contract.** The committed story-map slice from `define-release` is the authoritative boundary: UC elaboration surfaces unresolved alternative/failure paths *without* recreating or expanding release scope; out-of-scope `REQ`/`QAS` need an explicit change `DEC#` (LNT-16).
- **Trace rationale.** The shared linter (the Adapt of Problem-Based-SRS's mechanical validation — no `.spec` JSON, no `CP/CN/FR` IDs) enforces the chain; every `REQ`/`QAS` additionally traces to a need, risk, constraint, or obligation with its rationale, consuming the O/E/H classification from the `REL` (LNT-16).
- **QAS elicitation and gate.** ISO 25010-flavoured completeness prompts cover operational and stakeholder consequences without checklist inflation (no Obsidian schemas/tags/vault layout — donor license unverified, pattern-only); each critical QAS records the three gate dimensions **Complete / Measurable / Feasible** — independent review separation is mandatory, multi-agent fan-out optional; QAS drafting may conditionally call the `quality-attribute-scenario-writer` specialist per the §3.1 contract (depth-audit condition, pin, local-drafting fallback), with every candidate passing this same gate before a `QAS#` exists.
- **Integrations:** calls `domain-modeling` when new terms/rules surface (`domain-glossary.md` and `CONTEXT.md` stay canonical; §3.1 call contract); `grill-with-docs` as the validation review. Its output — the specified slice — is this skillset's terminal artifact; what consumes it is the future design skillset's concern (§7).
- **Guardrails:** flags vague terms ("fast", "secure") without measurable criteria; every `REQ` needs a verification method or an explicit open marker (canonical `OPEN:` syntax, §2.2); invented paths, targets, terms, or rules are marked as proposals requiring confirmation — a proposal can never pass as a completed value (LNT-05).
- **Handover and backtracking:** the final output names the design-readiness status, exact artifacts, open questions, required human confirmations, validation hooks, and the next workflow selected by tailoring; failed gates route to a named target — back to `define-release`, `discover-product`, `domain-modeling`, or human confirmation — instead of forcing completion, each route naming the target artifact and owner. The final output instantiates the §4.1 handover contract — the design-readiness status is the progression gate (the readiness-for-design checklist plus the linter set below), the exact artifacts are the changed set, the open questions and required human confirmations are the unresolved decisions the next stage inherits, the next workflow comes from the one-pager, and any recorded skip passed over is named. Each failed-gate route is a §4.2 route, and §4.2's post-release conditions 3, 5, 6, and 10 re-enter the loop at this skill.
- **Singular accountable ownership and specialist verdicts:** every consequential requirements decision the human gate resolves — invented failure paths, target values, domain rules, scope changes, consequential trade-offs — is recorded in its `DEC#` with the one named accountable owner from `lifecycle-onepager.md`'s decision-authority record (§5.3); a group or department as owner is refused (RTS-07), and the handover lists unresolved decisions with their owners. The QAS gate's **Feasible** dimension passes only on a recorded engineering/domain/operations/security reviewer verdict or a blocking-uncertainty `OPEN:` marker escalated to the human gate — never auto-passed (RTS-08). The builder must not fabricate specialist evidence: invented stakeholder judgment, domain rules, failure behavior, or measurable targets stay flagged proposals that cannot pass as completed values (LNT-05), and the critic checks for unmarked invention. Each failed-gate route carries the owner and escalation path from the one-pager, and the skill refuses to elaborate a `REL` slice whose upstream `OPP`/`ASM`/`REL` has been invalidated unless perseverance is recorded with its rationale as a `DEC#` (RTS-10).
- **Finalize runs the deterministic linter (§2.2):** LNT-01, LNT-03–LNT-05, LNT-10 (`REQ` verification method or open marker), LNT-11 (`QAS` six fields, open markers, measurable `Measure:`), LNT-12 (transition requirements for retired scope), LNT-16 (trace rationale and scope boundary), LNT-21 (no `proposed` `DEC#` survives finalize); the human review gate's judgment findings stay separate.

### 5.7 `validate-release` (new)

- **Mode:** short interview per review cadence.
- **Analysis-planning gate.** Before any result is inspected, the skill writes a durable, timestamped analysis plan into `validation/REL<n>-review.md` — review question and decision owner, the unchanged precommitted criteria, metric definitions (outcome vs driver vs input vs usage vs guardrail), population/segments/time window, qualitative and operational evidence sources, quality limitations, confounders, evidence-strength rules, and the persevere/adapt/pause/retire decision rules. Any post-hoc plan change is a dated `DEC#` with the original visible (LNT-17). Independently authored mechanism — the inspiring repository has no stated license, so nothing is copied.
- **Does:** compare observed outcomes against `REL`'s success/guardrail/stop criteria; pull in evidence accumulated via `qa`/`triage` issues (§3.1 call contract — source-addressable observations only, with the manual-intake fallback); record the verdict and — the essential part — **what it reopens** (vision / opportunities / scope / requirements) as `DEC` entries plus new `EV` rows, then point at the loop re-entry. Post-release `EV#` rows use the shared Rich/Mixed/Thin strength model with the source-quality confidence cap — volume never inflates confidence (LNT-18).
- **Metric audit.** When outcome-metric hygiene is material, the review runs the version-pinned `north-star` specialist per the §3.1 contract — vanity-metric refusal, driver/input decomposition — preserving result, warnings, or the justified skip in the review; locally authored metric-tree material (adapted from MIT phuryn sources) structures the local-fallback review; no second runtime dependency.
- **Context-separated verifier.** Where the review includes substantial derive work, evidence extraction is separated from verdict review: the verifier sees raw evidence, precommitted criteria, candidate findings, and gates — not the analyst's intended conclusion; confirmation-bias fixtures exercise this in §6.
- **Re-entry matrix and handover.** A re-entry/backtracking matrix — an independently authored pattern (the ForceInjection donor license is WIP/unverified, so nothing is copied) — routes each finding to the challenged decision, the reopened artifact, one owner, required evidence, the next skill, and a closure condition; generic "revisit earlier work" fails. The review ends with a handover naming the verdict, reopened artifacts with exact IDs, named owners, next skill, exact input files, urgency, and preserved (non-reopened) decisions; perseverance is recorded with rationale just as reopening is. The matrix's rows are exactly the ten-condition map in §4.2 — each post-release finding class routes to the artifact and skill reopened, including the `domain-modeling` external-call route (condition 7, per §3.1) and the measurement-repair non-route (condition 9) — and the closing handover instantiates §4.1 with the verdict and urgency added as this skill's route-level fields.
- **Vision-stability escalation guard:** the matrix's condition-8 route is the only path to the vision, and it is guarded by the §4 pivot definitions — **only evidence contradicting a foundational actor/outcome/value/principle/boundary assumption routes to the vision, via an explicit `DEC#` citing that invalidating evidence**; `validate-release` routes, it never edits the vision. Every other finding (conditions 1–7, 9, 10) is a discovery pivot reopening downstream artifacts — a finding explained by a lower-level opportunity, scope, journey, requirement, or `QAS` never escalates past it, and each route is labeled discovery pivot or vision pivot in the review. A failed release or failed experiment offered as vision-rewrite grounds is refused and rerouted downstream (RTS-11); the genuine foundational contradiction proceeds only with the `DEC#` (RTS-12, §4.2 condition 8).
- **Review and re-entry ownership; specialist evidence:** the analysis plan's decision owner and every re-entry route's owner are one named accountable individual per `lifecycle-onepager.md`'s decision-authority record (§5.3) — a team or department as owner fails the review or route (RTS-07). Findings in specialist territory — operational evidence, guardrail breaches, incidents, audit/compliance findings — require a source-addressable specialist `EV#` (via the `qa`/`triage` intake or the analysis plan's operational-evidence sources) or an explicit `OPEN:` marker; specialist evidence is never fabricated (RTS-08). A re-entry crossing a decision-authority boundary names the owner and escalation path from the one-pager (RTS-09), and no route is closed — and no dependent work continued — while its reopened artifact is unresolved, unless perseverance is recorded with its rationale as a `DEC#` (RTS-10).
- **Guardrail:** shipping is not success; a review that measures nothing but "it shipped" is flagged as such.
- **Runs the deterministic linter (§2.2) before routing findings:** LNT-01, LNT-03–LNT-05, LNT-17, LNT-18, LNT-21, so every reopened `REQ/QAS/CAP/OPP` reference resolves before re-entry and the downstream impact list is complete; it consumes LNT-09's guarantee — an outcome that cannot be observed yields measurement repair, never a fabricated verdict.
- **Regression hooks:** scenarios RTS-06 (post-release reopening), RTS-10 (invalidated upstream artifacts), RTS-11 (over-escalation refused), and RTS-12 (vision pivot with `DEC#`) of the reference-topic rubric (§6) exercise this skill's routing and refusal behavior.

## 6. Skillset regression validation

The deterministic linter (§2.2) guards the *artifacts*; this section guards the *skills*. One small **reference topic** — fixed, vendored with the skillset alongside its fixtures and scored run reports, never part of any real product workspace — is run end-to-end (greenfield entry: `tailor-lifecycle`, both vision skills, the loop, `validate-release`) **after each skill is authored or materially changed**. The run is blind: the executing agent gets the topic and the skills, never the expected outcomes; scoring compares the produced workspace and transcripts against the rubric below.

**Scoring axes.** Every run is scored on four axes, with deterministic and judgment results reported separately (§2.2 rule):

1. **Method-doc completion checks** — each skill's finalize gate re-runs its stage doc's completion checks per the §2.1 mapping; every check passes or leaves an explicit `OPEN:` stub.
2. **Linter results** — a full LNT-01–LNT-21 sweep (§2.2) over the produced spine + workspace at the end of the run, plus each skill's finalize check set from §5.
3. **Handover** — every skill's closing output carries the five §4.1 contract fields, naming the next applicable stage per `lifecycle-onepager.md` and the exact input artifacts; chaining never overrides tailoring (§4.1 guardrail).
4. **Re-entry** — reopened artifacts are cited with resolvable IDs (LNT-03), each reopen is a §4.2 route, and the loop re-enters at the reopened artifact per §4.

**Failure handling.** Every failed scenario or axis is recorded in the scored run report, attributed to the responsible skill — or to this plan when the design itself is at fault — and that skill or plan section is updated and the run repeated before the change is accepted.

**Scenarios.** Each scenario has a stable ID that authoring-time tests cite as objective evidence, so IDs are append-only: new scenarios get new IDs, and a retired scenario keeps its ID with a retirement note. Scenarios run as variants of, or seeded probes on, the one reference topic (two tailoring variants exist: low-ceremony and high-coordination).

| ID | Scenario | Pass condition |
| --- | --- | --- |
| RTS-01 | Low ceremony | The low-ceremony variant completes with the minimum package and explicit `OPEN:` stubs (LNT-05); no skill inflates ceremony beyond the one-pager (design principle 5); no roadmap is demanded. |

| RTS-03 | Weak evidence | Seeded opinion/hypothetical input is classified as weak evidence (Rich/Mixed/Thin) and confidence stays capped by evidence quality (LNT-18); an `EV#` row without a human-supplied source, date, and strength fails LNT-06. |
| RTS-04 | Single-solution exception | The single-solution fixture is below the ≥3 materially different directions threshold: with only one `SOL#` direction on the table, `discover-product` refuses assumption ranking *at ranking time* (§5.4 guardrail); with a `DEC#` recording why alternatives are not viable, ranking proceeds and LNT-07's ≥3-directions-or-`DEC#` rule passes; the finalize check *alternative solutions were considered* is scored explicitly. |
| RTS-05 | Requirements gap needing human review | `specify-requirements` hits a gap only a human can settle (an invented failure path, an unsettled target value); the gap reaches the human review gate as an explicit `OPEN:` item (LNT-05, LNT-10, LNT-11), never a fabricated value. Per-skill fixture obligations feed this suite rather than duplicating it: `derive-vision-spine`'s end-to-end matrix and mutation tests, `discover-product`'s blind reference run and mutation set, `tailor-lifecycle`'s scored reference run, and `validate-release`'s blind-verifier / confirmation-bias fixtures all execute as part of, or alongside, the reference-topic run and are scored on the same four axes.

## 7. Scope boundary — what this skillset does not build

This skillset ends at the [readiness-for-design checklist](../overview.md#readiness-for-software-design); its terminal artifact is the specified slice. The exclusions below are deliberate, not gaps to fill:

- **Design** — `design-an-interface`, `codebase-design`, `improve-codebase-architecture`, `prototype`'s UI-variations branch, `domain-modeling`'s ADR work. A separate plan; it *consumes* this skillset's output. Only `prototype`'s state-model branch is in scope here (§3.1). Design and architecture authority stays with engineering, never product management by default (§5.3).
- **Implementation planning / delivery** — `to-prd` and `to-issues` convert committed scope into tracker artifacts. Excluded so the loop's output stays a product artifact, not a backlog; no skill here may write to an issue tracker.
- **Implementation / testing** — `tdd`, `verify`, `review`, `code-review`. Relevant only as the origin of the post-release evidence `validate-release` consumes via the `qa`/`triage` intake contract (§3.1).
